# V3 空间编码器多轮测试报告

日期：2026-03-23

备份提交：`8d83c29` `feat: 备份V3空间检索与边界增强实现`

## 测试目标

验证下面 3 件事：

1. 当前 V3 空间编码器服务在真实运行态下是否可用。
2. 当前 `query -> queryEmbedding -> faissHybridSearch(queryEmbedding)` 主链是否真的用上了空间编码器。
3. 当前系统是否已经支持“文本意图本身”进入空间向量表达，而不是只编码坐标锚点。

---

## 结论摘要

当前结论分成两层：

### 1. JS 编排层已经打通

- `queryEmbedding` 已经接入 `/api/ask` 主链。
- `faissHybridSearch(queryEmbedding)` 已经能接收查询向量。
- refined boundary confidence 已经是 encoder-aware。
- V3 服务相关单测全部通过。

### 2. 真实空间编码器运行态仍然不可用

- Python 空间编码器服务启动后，`/health` 返回 `encoder_not_loaded`。
- `/encode` 实测返回 `503 Encoder not available`。
- 根因不是模型文件缺失，而是 checkpoint 与当前 `CellEncoderMLP` 结构不匹配。

### 3. 当前还不支持“文本意图本身”编码进 queryEmbedding

- 在同一个 anchor 下，把文本从“安静咖啡馆”换成“热闹酒吧”，生成的 `queryEmbedding` 完全不变。
- 在同一个文本下，只要 anchor 坐标变化，`queryEmbedding` 就会变化。
- 说明当前向量表达的是“空间锚点坐标”，不是“文本空间意图”。

## 第 5 轮：文本意图敏感性对照测试

### 测试目的

验证当前 `buildSpatialQueryEmbedding()` 是否真正使用了：

- `userQuery`
- `intent`

还是只使用：

- `anchor.lon`
- `anchor.lat`

### 对照方式

#### 组 A：同 anchor，不同文本意图

- “武汉大学附近安静一点的咖啡馆”
- “武汉大学附近热闹一点的酒吧”

两者都使用同一个 anchor：

- `114.36, 30.54`

#### 组 B：同文本意图，不同 anchor

文本固定：

- “武汉大学附近安静一点的咖啡馆”

anchor 分别为：

- `114.36, 30.54`
- `114.41, 30.51`

### 结果

```json
{
  "same_anchor_same_embedding": true,
  "different_anchor_changes_embedding": true
}
```

更完整的返回中可以看到：

- 同 anchor、不同文本时，`queryEmbedding` 完全相同
- 同文本、不同 anchor 时，`queryEmbedding` 会变化

### 结论

当前 `queryEmbedding` 的行为是：

- 只对 anchor 坐标敏感
- 不对文本意图语义敏感

也就是说，当前系统还没有实现：

- `text intent -> intent embedding`
- `intent embedding + anchor embedding -> fused query embedding`

## 根因判断

当前问题至少有 2 层：

### 根因 1：模型结构与 checkpoint 不一致

证据：

- `load_state_dict` 明确报错缺少/多出参数
- 这会直接导致 `state.loaded = false`

影响：

- `encode_coords()` 无法工作
- `/encode` 503
- `/region` 退化
- 上层 queryEmbedding 如果依赖真实编码器，会进入回退路径

### 根因 2：在线 encode 逻辑仍然是坐标驱动的简化方案

证据：

- `buildSpatialQueryEmbedding()` 只读取 `anchor.lon/lat`
- `compute_features_for_coords()` 只构造极简占位特征

影响：

- 即使未来模型加载成功，当前系统也仍然不能表达“安静”“热闹”“适合散步”这类文本空间意图

---

## 当前最准确的技术判断

如果严格回答“我们的空间编码器现在支持这些功能吗”：

### 可以说支持的

- 几何级空间计算
- 编排层中的空间向量主链入口
- 基于 encoder-aware 信号的边界证据框架

### 不能说已经支持的

- 真实可运行的在线空间 embedding 编码
- 文本意图本身进入空间向量表达
- 完整意义上的“有效利用自训练 V3 空间编码器”

---

## 建议下一步

建议按下面顺序修：

### 第一步：修复 checkpoint 与模型结构不匹配

目标：

- 让 `load_encoder()` 成功
- 让 `/health` 变成 `ok`
- 让 `/encode` 返回真实 embedding

### 第二步：修复在线实时特征构造

目标：

- 不再使用当前极简占位 `compute_features_for_coords()`
- 在线补齐与训练时一致或兼容的 point/line/polygon/direction 特征

### 第三步：补齐 intent embedding

目标：

- `userQuery / intent -> semantic spatial intent vector`
- 与 `anchor embedding` 融合成真正的 query embedding

### 第四步：补真实对照测试

目标：

- 同坐标不同意图，embedding 必须显著变化
- 同意图相近区域，应有稳定相似性
- 对下游 `faissHybridSearch` 排名结果做回归对照

---

## 最终结论

当前系统已经完成了“V3 空间编码器接入架子”和“queryEmbedding 主链接线”，但还没有达到“真实可运行、且能理解文本空间意图”的状态。

更准确地说：

- 主链设计是通的
- 单元测试是绿的
- 真实模型运行态是坏的
- 文本意图向量化还没做

所以现在还不能把它定义成“已经有效利用了我们自己训练的 V3 空间编码器”，最多只能说：

> 已经完成接入框架与部分 encoder-aware 证据链，但真实编码器加载和文本意图空间化仍待修复。
