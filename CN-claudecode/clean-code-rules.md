# AI 代码生成清洁代码规则

这些规则指导代码生成以产生可维护的、专业质量的代码。

## 有意义的名称
- 使用揭示意图的名称，解释为什么某物存在
- 避免误导和毫无意义的区分（如 `data`、`info`、`manager`）
- 使用可读、可搜索的名称
- 类名：名词（如 `UserAccount`、`PaymentProcessor`）
- 方法名：动词（如 `calculateTotal`、`sendEmail`）
- 避免心理映射和编码（Hungarian notation、前缀）

## 函数
- 保持函数简短（理想 < 20 行）
- 只做一件事 — 单一职责原则
- 每个函数一个抽象级别
- 限制参数：0-2 个理想，3 个最大，避免标志参数
- 无副作用 — 函数应该名副其实
- 将命令（改变状态）和查询（返回信息）分开
- 优先使用异常而非错误码

## 注释
- 代码应该不言自明 — 尽可能避免注释
- 好的注释：法律信息、警告、TODO、公共 API 文档
- 坏的注释：冗余、误导或解释糟糕代码
- 永不注释掉代码 — 删除它（版本控制保留历史）
- 如果你需要注释，考虑重构代码

## 格式化
- 保持文件小而专注
- 垂直格式化：相关概念放在一起，空白行分隔概念
- 水平格式化：限制行长度（80-120 字符）
- 使用一致的缩进和团队风格
- 将相关函数分组在一起

## 对象和数据结构
- 对象：把数据隐藏在抽象后面，通过方法暴露行为
- 数据结构：暴露数据，有最小行为
- Demeter 法则：只和直接朋友交谈，避免 `a.getB().getC().doSomething()`
- 不要盲目通过 getter/setter 暴露内部结构

## 错误处理
- 使用异常而非返回码或错误标志
- 当代码可能失败时先写 `try-catch-finally`
- 在异常消息中提供上下文
- 不要返回 `null` — 返回空集合或使用 Optional/Maybe
- 不要传递 `null` 作为参数

## 类
- 小类：按职责而非行数衡量
- 单一职责原则：一个更改原因
- 高内聚：类变量被多个方法使用
- 低耦合：类之间最小依赖
- 开闭原则：对扩展开放，对修改关闭

## 单元测试
- 快速、独立、可重复、自我验证、及时（F.I.R.S.T.）
- 每个测试一个断言（或一个概念）
- 测试代码质量等同于生产代码质量
- 使用描述被测试内容的可读测试名
- Arrange-Act-Assert 模式

## 代码质量原则
- **DRY（不要重复自己）**：无重复
- **YAGNI（你不需要它）**：不要为假设的未来构建
- **KISS（保持简单）**：避免不必要的复杂性
- **童子军规则**：离开时让代码比你发现时更干净

## 应避免的代码味道
- 长函数或类
- 重复代码
- 死代码（未使用的变量、函数、参数）
- 特性依恋（方法对其他类更感兴趣）
- 不当亲密（类之间了解太多）
- 长的参数列表
- 原始类型痴迷（过度使用原始类型而非小对象）
- Switch/case 语句（考虑多态）
- 临时字段（有时才使用的类变量）

## 并发
- 将并发代码与其他代码分开
- 限制同步/锁定数据的范围
- 使用线程安全集合
- 保持同步部分小
- 了解你的执行模型和原语

## 系统设计
- 将构造与使用分开（依赖注入）
- 使用工厂、构建器创建复杂对象
- 面向接口编程而非实现
- 优先组合而非继承
- 当模式简化时应用设计模式，而非炫耀

## 重构
- 持续重构，而非大批量
- 前后始终有通过的测试
- 小步前进：一次一个更改
- 常见重构：提取方法、重命名、移动、内联

## 文档
- 自文档化代码 > 注释 > 外部文档
- 公共 API 需要清晰的文档
- 在文档中包含示例
- 让文档靠近代码（理想在代码中）

---

**核心哲学**：代码阅读次数是编写次数的 10 倍。为可读性和可维护性优化，而非巧妙。
