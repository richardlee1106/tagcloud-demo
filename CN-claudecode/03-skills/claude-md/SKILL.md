## 用户输入

```text
$ARGUMENTS
```

你**必须**在继续之前考虑用户输入（如果非空）。用户可能指定：
- `create` - 从头创建新的 CLAUDE.md
- `update` - 改进现有的 CLAUDE.md
- `audit` - 分析并报告当前 CLAUDE.md 的质量
- 特定路径以创建/更新（如 `src/api/CLAUDE.md`，用于目录级指令）

## 核心原则

**LLM 是无状态的**：CLAUDE.md 是唯一在每个会话中自动包含的文件。它作为 AI 智能体进入代码库的入门文档。

### 黄金法则

1. **少即是多**：前沿 LLM 可以遵循约 150-200 条指令。Claude Code 的系统提示已占用约 50 条。让你的 CLAUDE.md 专注简洁。

2. **普遍适用性**：只包含与每个会话相关的信息。任务特定指令属于单独文件。

3. **不要用 Claude 做 Linter**：风格指南会膨胀上下文并降低指令遵循能力。使用确定性工具（prettier、eslint 等）代替。

4. **绝不自动生成**：CLAUDE.md 是 AI 工具链的最高杠杆点。手工精心制作，考虑周全。

## 执行流程

### 1. 项目分析

首先，分析当前项目状态：

1. 检查现有 CLAUDE.md 文件：
   - 根目录：`./CLAUDE.md` 或 `.claude/CLAUDE.md`
   - 目录级：`**/CLAUDE.md`
   - 全局用户配置：`~/.claude/CLAUDE.md`

2. 识别项目结构：
   - 技术栈（语言、框架）
   - 项目类型（monorepo、单应用、库）
   - 开发工具（包管理器、构建系统、测试运行器）

3. 审查现有文档：
   - README.md
   - CONTRIBUTING.md
   - package.json、pyproject.toml、Cargo.toml 等

### 2. 内容策略（是什么、为什么、怎么做）

围绕三个维度构建 CLAUDE.md：

#### 是什么 - 技术与结构
- 技术栈概览
- 项目组织（对 monorepo 尤其重要）
- 关键目录及其用途

#### 为什么 - 目的与背景
- 项目做什么
- 某些架构决策为何做出
- 各主要组件负责什么

#### 怎么做 - 工作流程与约定
- 开发工作流程（bun vs node、pip vs uv 等）
- 测试程序和命令
- 验证和构建方法
- 关键的"陷阱"或非显而易见的注意事项

### 3. 渐进式披露策略

对于较大的项目，建议创建 `agent_docs/` 文件夹：

```
agent_docs/
  |- building_the_project.md
  |- running_tests.md
  |- code_conventions.md
  |- architecture_decisions.md
```

在 CLAUDE.md 中，用类似以下方式引用这些文件：
```markdown
有关详细构建说明，请参阅 `agent_docs/building_the_project.md`
```

**重要**：使用 `file:line` 引用而非代码片段，以避免过时的上下文。

### 4. 质量约束

创建或更新 CLAUDE.md 时：

1. **目标长度**：低于 300 行（最好低于 100 行）
2. **无风格规则**：移除任何 linting/格式化指令
3. **无任务特定指令**：移至单独文件
4. **无代码片段**：使用文件引用代替
5. **无冗余信息**：不要重复 package.json 或 README 中的内容

### 5. 必需部分

结构良好的 CLAUDE.md 应包含：

```markdown
# 项目名称

简要的一行描述。

## 技术栈
- 主要语言和版本
- 关键框架/库
- 数据库/存储（如有）

## 项目结构
[仅对 monorepo 或复杂结构]
- `apps/` - 应用入口点
- `packages/` - 共享库

## 开发命令
- 安装：`命令`
- 测试：`命令`
- 构建：`命令`

## 关键约定
[仅限不显而易见、影响重大的约定]
- 约定 1 及简要解释
- 约定 2 及简要解释

## 已知问题 / 陷阱
[总是让开发者绊倒的事项]
- 问题 1
- 问题 2
```

### 6. 应避免的反模式

**不要包含：**
- 代码风格指南（使用 linter）
- 如何使用 Claude 的文档
- 显而易见模式的冗长解释
- 复制粘贴的代码示例
- 通用最佳实践（"编写干净代码"）
- 特定任务的指令
- 自动生成的内容
- 冗长的 TODO 列表

### 7. 验证清单

定稿前验证：

- [ ] 低于 300 行（最好低于 100 行）
- [ ] 每行适用于所有会话
- [ ] 无风格/格式化规则
- [ ] 无代码片段（使用文件引用）
- [ ] 命令经核实可用
- [ ] 复杂项目使用了渐进式披露
- [ ] 记录了关键陷阱
- [ ] 与 README.md 无冗余

## 输出格式

### 对于 `create` 或默认：

1. 分析项目
2. 按照上述结构起草 CLAUDE.md
3. 呈现草稿供审查
4. 批准后写入适当位置

### 对于 `update`：

1. 阅读现有 CLAUDE.md
2. 根据最佳实践审核
3. 识别：
   - 要移除的内容（风格规则、代码片段、任务特定内容）
   - 要精简的内容
   - 缺少的基本信息
4. 呈现变更供审查
5. 批准后应用变更

### 对于 `audit`：

1. 阅读现有 CLAUDE.md
2. 生成报告，包括：
   - 当前行数 vs 目标行数
   - 普遍适用内容百分比
   - 发现的反模式列表
   - 改进建议
3. **不要**修改文件，只报告

## AGENTS.md 处理

如果用户请求创建/更新 AGENTS.md：

AGENTS.md 用于定义专业智能体行为。与 CLAUDE.md（用于项目上下文）不同，AGENTS.md 定义：
- 自定义智能体角色和能力
- 智能体特定指令和约束
- 多智能体场景的工作流程定义

应用类似原则：
- 保持专注简洁
- 使用渐进式披露
- 引用外部文档而非嵌入内容

## 备注

- 在包含命令前始终验证其可用
- 有疑问时省略——少即是多
- 系统提示告诉 Claude CLAUDE.md"可能相关也可能不相关"——噪音越多，越容易被忽略
- Monorepo 最受益于清晰的"是什么/为什么/怎么做"结构
- 目录级 CLAUDE.md 文件应更加专注
