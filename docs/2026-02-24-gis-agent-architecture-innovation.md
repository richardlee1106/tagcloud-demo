# GIS Agent 架构创新路线（方案文档，暂不实施）

> 日期：2026-02-24  
> 目标：显著提升 GIS Agent 的分析能力、响应速度和可扩展性。  
> 说明：本文件仅给出推理与方案，不修改现有线上逻辑。

---

## 1. 现状瓶颈（能力与速度）

1. 交互层瓶颈
- 地图交互与证据渲染存在同线程竞争，复杂图层下容易出现交互卡顿。
- AI 面板承担过多职责（流式事件、语义归一化、组件调度、联动动作），导致可维护性与迭代速度下降。

2. 算法层瓶颈
- 区域命名、地名标签、机会洞察等仍偏规则驱动，跨城市/跨语境泛化受限。
- 多阶段推理链路（planner -> spatial -> fusion -> writer）缺少统一的“质量反馈回路”。

3. 架构层瓶颈
- SSE 事件协议虽可用但弱类型，前后端演进时存在隐式耦合风险。
- Python 空间管线能力强，但缺少“可复用中间结果缓存层”，导致重复查询成本高。

---

## 2. 三条可选升级路线

## 路线 A：稳态增强（低风险，优先推荐）

### 核心思路
- 保持现有技术栈不变（Vue + Fastify + Python），在协议、缓存、模块化层面做结构化升级。

### 关键动作
1. 协议标准化
- 为 `stage/progress/refined_result` 统一 JSON schema，并在前后端双向校验。

2. 中间结果缓存
- 为 Python 管线引入多层缓存：
  - L1：查询计划缓存（query_plan hash）
  - L2：空间候选集缓存（geometry + category + viewport hash）
  - L3：聚类/区域建模缓存（cluster params + candidate ids hash）

3. 前端模块化
- 拆分 `AiChat` 与 `MapContainer` 的大组件，形成 composables + service 层。

### 预期收益
- 开发效率提升、线上回归风险下降。
- 重复查询延迟明显下降（典型场景 25%-45%）。

### 风险/成本
- 风险低，主要是改造期间需要保持兼容接口。
- 成本中等（2-4 周）。

---

## 路线 B：性能优先（中风险，高收益）

### 核心思路
- 将几何密集计算从 Python 解释层进一步下沉到高性能层，减少大规模要素处理时延迟波动。

### 关键动作
1. 热点函数加速
- 对高频几何操作（buffer/intersection/point-in-polygon/coverage）做 Rust/C++ 扩展模块。
- 通过 Python FFI（pyo3/cffi）保留现有 pipeline 调度逻辑。

2. 增量式区域建模
- 对连续查询复用上一次的候选池和聚类结构，只增量更新变化边界范围。

3. 前端渲染层分级
- 低缩放级别使用抽样/聚合图层，高缩放再切回细粒度图层。

### 预期收益
- 高负载下 tail latency（P95/P99）改善明显。
- 大选区复杂查询稳定性显著提升。

### 风险/成本
- 风险中等（跨语言调试复杂）。
- 成本中高（4-8 周）。

---

## 路线 C：能力跃迁（高风险，战略向）

### 核心思路
- 以“可解释 + 可学习 + 可评估”的 Agent 平台化能力为目标，形成闭环学习系统。

### 关键动作
1. Agent 反馈学习闭环
- 将用户点击、追问、地图定位行为作为弱监督反馈，训练 reranker/策略模型。

2. 多模型协同调度
- Planner / Spatial / Writer 分别使用最适配模型，采用路由器动态选模型与预算。

3. 评估基线体系
- 建立离线评测集（地名相关性、边界可信度、策略可执行性、响应时延）。

### 预期收益
- 能力上限更高，支持更复杂业务场景（选址、竞对、风险评估）。

### 风险/成本
- 风险高（工程+算法+数据治理同步要求高）。
- 成本高（8-16 周，需专门评测与数据工程投入）。

---

## 3. 推荐策略（组合拳）

## 推荐顺序
1. 先做路线 A（稳态增强）
- 原因：收益确定、风险低，可快速降低维护成本和线上波动。

2. 再引入路线 B 的局部能力
- 原因：把性能瓶颈集中打掉，尤其是热点几何计算。

3. 最后评估路线 C 的 ROI
- 原因：战略升级需要稳定基础，否则投入产出比不稳。

---

## 4. 可量化目标（建议 KPI）

1. 速度
- P50 响应时间：降低 20%-30%
- P95 响应时间：降低 35%-50%
- 地图交互帧率：复杂场景维持 45 FPS 以上

2. 质量
- 地名标签相关性（人工标注 Top-10）：提升 15%+
- 片区命名可接受率：提升 10%+
- 对比分析可执行性评分：提升 20%+

3. 稳定性
- 前后端协议字段不一致导致的线上错误：降到接近 0
- 回归修复平均时长（MTTR）：下降 25%+

---

## 5. 分阶段落地建议

## Phase 1（2 周）
- 统一 SSE schema
- 前端大组件拆分设计
- 中间结果缓存 PoC

## Phase 2（3-4 周）
- 缓存体系接入主链路
- 热点几何函数基准测试与加速 PoC
- 建立性能与质量监控看板

## Phase 3（4-8 周）
- 选择 1-2 个高价值场景上线性能增强模块
- 建立反馈学习样本采集与评估流程

---

## 6. 结论

- 若目标是“短期见效 + 可控风险”，优先执行路线 A。  
- 若目标是“高负载稳定 + 速度跃升”，在 A 稳定后推进路线 B。  
- 若目标是“能力上限突破”，在 A/B 建好工程地基后再做路线 C。  

当前系统最佳出路不是推翻重来，而是先做结构化解耦与缓存，然后再把性能热点下沉和能力闭环逐步引入。
