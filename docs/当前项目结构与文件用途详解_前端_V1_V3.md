## 1. 前端：`src/`

### 1.1 前端在整个项目里的角色

前端是整个 GeoLoom-RAG 的可视化工作台，负责把地图、标签云、AI 对话、叙事模式、V2 链路观测这些能力组织到一个统一界面里。

当前前端有两种常见运行形态：

| 运行方式 | 含义 |
|---|---|
| `npm run dev:stack` | 前端以默认模式启动，并连接 `V1-fastify-backend` |
| `npm run dev:V3` | 前端以 V3 模式启动，并连接 `V3-GeoEncoder-RAG` |

也就是说，前端本身不是只服务一个后端，而是承担“统一 UI 壳层”的职责，然后通过环境变量和请求封装切换 V1 / V3。

### 1.2 前端入口与骨架文件

| 路径 | 释义 | 用途 |
|---|---|---|
| `src/main.js` | Vue 应用启动入口 | `createApp(App)` 后挂载路由，是前端最外层启动文件。 |
| `src/App.vue` | 根组件壳 | 自己几乎不做业务，只负责放 `<router-view>`。 |
| `src/router/index.js` | 路由配置中心 | 当前把 `/` 指向主工作台 `MainLayout.vue`，把 `/narrative` 指向叙事页面 `NarrativeMode.vue`。 |
| `src/MainLayout.vue` | 主工作台编排层 | 这是前端最核心的文件，负责把地图、控制面板、标签云、AI 面板、选区状态、地图联动都串起来。 |
| `src/config.js` | 接口基址配置 | 负责在开发态 / 生产态下解析 AI API 与 Spatial API 的 base URL，也承担 V1/V3 切换时的地址分发。 |
| `src/style.css` | 全局样式基线 | 放全局基础样式和页面级通用样式。 |
| `src/MainLayout.vue.garbled.bak` | 备份文件 | 明显是历史修复/编码备份文件，不参与运行，不建议继续扩散引用。 |

## 2. 后端 V1：`V1-fastify-backend/`

### 2.1 V1 在整个项目里的角色

`V1-fastify-backend` 是当前默认开发链路中的主后端，主要特点是：

| 能力 | 说明 |
|---|---|
| HTTP 网关 | 用 Fastify 暴露 `/api/ai`、`/api/jobs`、`/api/spatial`、`/api/search`、`/api/category`、`/api/ops` |
| 任务编排 | 用队列和 worker 管理空间任务与叙事任务 |
| Python 桥接 | 通过 gRPC 把复杂空间计算交给 `python_service/` |
| 兼容层 | 同时承接旧链路、灰度迁移、模板学习、审计与运维指标 |

从职责上说，V1 更像“生产型网关 + 历史兼容层 + 运维可观测中心”。

### 2.4 V1 服务层：`V1-fastify-backend/services/`

这层是 V1 真正的“大脑”，大体可以分为 5 类：连接层、编排层、规则层、观测层、结果层。

#### 2.4.1 连接与底座能力

| 路径 | 释义 | 用途 |
|---|---|---|
| `V1-fastify-backend/services/database.js` | 数据库访问层 | 负责 PostgreSQL / PostGIS 连接、查询与部分计时写入。 |
| `V1-fastify-backend/services/vectordb.js` | 向量访问层 | 封装向量检索或混合检索能力。 |
| `V1-fastify-backend/services/grpcClient.js` | gRPC 客户端 | 把 Node 请求送到 Python 计算服务，并接收流式事件。 |
| `V1-fastify-backend/services/queue.js` | 队列服务 | 封装 BullMQ / memory 队列、任务 enqueue、事件订阅。 |
| `V1-fastify-backend/services/geocoder.js` | 地理编码器 | 把地点名转成空间锚点或坐标。 |
| `V1-fastify-backend/services/llm.js` | LLM Provider 层 | 负责 LLM 可用性、模型发现、基础调用。 |
| `V1-fastify-backend/services/llmService.js` | LLM 服务封装 | 进一步承接更高层的 LLM 调用组织。 |

### 3.1 V3 在整个项目里的角色

## 4. 空间编码器研究区：`spatial_encoder/`

### 4.1 `spatial_encoder/` 在整个项目里的角色

这一块更像是“项目里的研究中心”，主要负责空间编码器的训练、验证、导出、模型保存和 API 化试验。

它和 `V1-fastify-backend/`、`V3-GeoEncoder-RAG/` 的关系可以理解成：

| 模块 | 角色 |
|---|---|
| `spatial_encoder/` | 训练模型、验证模型、导出 embedding 与实验结果 |
| `V1-fastify-backend/` | 调用或桥接空间能力，把训练结果转成服务能力 |
| `V3-GeoEncoder-RAG/` | 更直接地把空间编码器和混合检索挂到空间问答服务里 |

结合当前仓库结构、`README.md`、`CONTEXT.md` 与主工程说明来看，`v26_GLM/` 是当前最值得优先关注的训练与实验目录，`v23/`、`v24/`、`v26/` 更多承担历史阶段和统一骨架的作用。

## 7. 一句话总结

这个仓库现在可以理解成四层：

| 层 | 核心路径 | 你可以把它理解成 |
|---|---|---|
| 前端展示层 | `src/` | 地图、标签云、AI 工作台的统一 UI 外壳 |
| V1 综合后端 | `V1-fastify-backend/` | 默认主后端、任务编排中心、Python 计算桥接层 |
| V3 独立智能后端 | `V3-GeoEncoder-RAG/` | 新版空间编码器 RAG 服务，强调独立检索与小模型空间推理 |
| 空间编码器研究层 | `spatial_encoder/` | 训练、评估、导出、模型资产与研究方法论沉淀 |

如果后面还要继续“再整理一轮目录”，最值得继续优化的地方已经比较明确：

1. V1 里历史兼容与主链路代码仍然混得比较深，可以继续按“网关 / 编排 / 规则 / 观测 / Python”再细拆。
2. 前端 `utils/` 里 AI、分析、文本、导出工具已经不少，后续也可以再按 `ai/`、`analysis/`、`text/`、`export/` 拆子目录。
3. `spatial_encoder/v26_GLM/` 里的阶段实验脚本很多，后续可以按“训练 / 评估 / 实验 / 可视化 / 中间产物”再细分。
4. 根目录实验资产很多，后续最好继续收拢到 `experiments/`、`archives/` 或更清晰的资料目录中。
