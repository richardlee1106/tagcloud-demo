## 0. 先说结论

V4 不是在 V3 基础上打补丁，而是整系统重新设计：

```
V3: NL → planner LLM → 执行 → answer LLM → 文本       （两次 LLM，长链路）
V4: NL → 强模型大脑 → 调用原子 skills → 证据回传 → 直接回答  （一次 LLM，短链路）
```

**核心构件与系统创新引擎**：
- **确定性空间视图组件**：原长链路渲染升级为本地确定性协议渲染（Evidence View）、无缝衔接的置信度门控。
- **动态魂魄注入框架**：构建 Alive System Prompt 组合流、多维度的 Profile 偏好（Soul与User双模）体系。
- **中间件编排逻辑**：摒弃长流水线，进化为“低延迟”并发调用链，以及高插拔的渐进式原子技能挂载机制。
- **多级上下文网关**：实现独立的 Session 路由与 L0/L1/L2 异构生命周期的记忆分层策略。

**核心原则**：
1. 模型负责思考，skills 负责出证据
2. Evidence View 是确定性压缩，不是 LLM 自由发挥
3. SQL 安全三层锁是强模型接入前的护城河
4. 会话记忆让强模型"记得"本次 spatial session 里做过什么

## 1. 背景与问题定义

### 1.1 V3 暴露的核心问题

| 问题 | 根因 |
|------|------|
| 30-40s 延迟（简单题） | 两次 LLM 常驻主链路（planner + answer） |
| 站级/出口级数据混写 | 证据组织层薄，证据到表达有错位 |
| "配套分析题/比较题"题型路由 | 工具太重，泛化差 |
| 继续补 if/else 走回规则堆 | 架构层就不是 Agent |

### 1.2 V4 核心目标

> 做一个面对千变万化空间自然语言问题，仍能稳定理解意图、调用工具、拿真实空间证据、再生成最终回答的 Agent。

### 1.3 当前已有资产（可复用）

- **PostGIS**（565K POI，精确几何计算）
- **V3 空间编码器双塔**（UltimateSpatialEncoder，352维 embedding，POI级 F1=90%）
- **向量检索**（FAISS，混合检索管线）
- **V3 GeoEncoder RAG Server**（Node.js/Fastify，已有 planner_line / spatial_core / retrieval）
- **前端 AI 对话面板**（Vue 3，已有 chatPipeline.js）

### 2.2 架构设计原则

| 原则 | 说明 |
|------|------|
| **外部大脑** | 强模型在外部 API（Claude/GPT），本地只做 skills 执行和格式化 |
| **证据驱动** | 所有回答必须有明确证据来源，不得脑补 |
| **确定性优先** | Evidence View / Renderer 是纯本地代码，不走 LLM |
| **安全第一** | SQL 安全三层锁在强模型接入前必须立住 |
| **会话感知** | 强模型通过 Alive System Prompt 感知本次会话状态 |

### 2.3 设计理念的突破（从中间件堆砌迈向极简轻量智能体）

```
传统本地大脑型漫长链路:
NL → 本地调度器 → 自然语言解析器 → SRE → 预处理引擎 → 工具沙盒 → 用户 （堆砌大量硬编码与串行拦截）

传统多段长流水线架构:
请求 → 9段沉重中间件拦截 → 主节点LLM → 子协同编排系 → 外部空间库调用 → 用户 （易断线、超高延迟）

GeoLoom 极致短链路框架（外部大脑高速融合并发型）:
NL → GeoLoom编排层 → SRE指纹极速预检 → 强大脑API（一次请求并下发并发 Function Calling）→ Skills并行执行打包 → 面板无缝渲染呈现
```

## 3. 后端架构设计

### 3.1 技术栈

| 组件 | 技术选型 |
|------|---------|
| API Server | Fastify（复用 V3） |
| Agent 编排 | Node.js（GeoLoom 智能体引擎） |
| Skills 执行 | Python（PostGIS / 空间编码器 / 向量检索 / 路网） |
| LLM 调用 | OpenAI-compatible API（Claude / GPT / Qwen / Ollama） |
| 会话存储 | Redis（ShortTerm）+ 文件系统（LongTerm） |
| 向量检索 | FAISS（复用 V3 spatial_encoder） |
| 数据库 | PostgreSQL + PostGIS + pgvector（复用 V3） |
| 路网 | OSMNX（复用 V3） |

#### 3.3.1编排控制核心： GeoLoomAgent

```typescript
// src/agent/GeoLoomAgent.ts
class GeoLoomAgent {
  private sessionManager: SessionManager
  private skillRegistry: SkillRegistry
  private memoryManager: MemoryManager
  private llmProvider: LLMProvider
  private srePhase1: SREPhase1
  private evidenceViewFactory: EvidenceViewFactory
  private renderer: Renderer

  async chat(request: ChatRequest): Promise<ChatResponse> {
    const { session_id, user_query, spatial_context } = request

    // 1. Session 管理
    const session = await this.sessionManager.getOrCreate(session_id)

    // 2. 构建 Alive System Prompt
    const alivePrompt = this.alivePromptBuilder.build(session)

    // 3. 构建 tool schemas
    const toolSchemas = this.skillRegistry.getToolSchemas()

    // 4. 置信度预检（SRE Phase1）
    const preCheck = await this.srePhase1.run(user_query, spatial_context)
    if (preCheck.confidence < 0.55) {
      return this.confidenceGate.askConfirmation(preCheck, session)
    }

    // 5. 多轮 LLM (并发支持) Function Calling
    const toolCalls = []
    let evidenceBundle = null
    const MAX_TOOL_CALLS = 5 // 熔断器：防止 Token 爆炸与无限死循环
    const seenToolSignatures = new Set<string>() // 防幻觉死循环：记录调用指纹

    while (toolCalls.length < MAX_TOOL_CALLS) {
      const response = await this.llmProvider.chatWithTools({
        messages: session.historyMessages,
        system: alivePrompt,
        tools: toolSchemas,
      })

      if (!response.tool_calls || response.tool_calls.length === 0) {
        break // 模型决定输出文本
      }

      // 并发执行 Tool Calls (支持原生 Parallel Function Calling)
      const results = await Promise.all(response.tool_calls.map(async (call) => {
        // [防幻觉死循环] 指纹校验：拒绝连续发生一模一样的无效调用
        const sig = `${call.skill_name}.${call.action}(${JSON.stringify(call.payload)})`
        if (seenToolSignatures.has(sig)) {
          return { call, result: { error: '检测到重复调用同样的参数，产生幻觉回路。请更改参数（如扩大缓冲半径）或调用其他技能。' } }
        }
        seenToolSignatures.add(sig)

        const skill = this.skillRegistry.get(call.skill_name)
        const result = await skill.execute(call.action, call.payload)
        return { call, result }
      }))

      for (const { call, result } of results) {
        if (!result.error) {
          evidenceBundle = this.mergeEvidence(evidenceBundle, result)
        }
        toolCalls.push({ call, result })
        session.addMessage('tool', { call, result })
      }
    }
    
    // 熔断监控：如果达到阈值依然没有抓到充分证据，强制触发透明降级提示
    if (toolCalls.length >= MAX_TOOL_CALLS && (!evidenceBundle || !evidenceBundle.isSufficient)) {
      evidenceBundle = this.applyDegradation(evidenceBundle, '查询过于复杂或数据稀缺，多次尝试未能获取精确结果，为您返回周边近似数据')
    }

    // 6. Evidence View 压缩（协议驱动渲染）
    const evidenceView = this.evidenceViewFactory.build(
      user_query,
      evidenceBundle,
      spatial_context
    )

    // 7. Renderer 输出
    const answer = this.renderer.render(evidenceView)

    // 8. 记忆写入
    await this.memoryManager.logOperation(session_id, {
      user_query,
      tool_calls: toolCalls,
      evidence_view: evidenceView,
      answer,
    })

    return { answer, evidence_view: evidenceView, tool_calls, trace_id }
  }
}
```

#### 3.3.2 SQL 安全三层锁

```
Layer 1: get_schema_catalog()
  → 返回最小可用 schema 描述，不是全库细节
  → 遍历 FROM 子句以验证表名白名单（拦截伪装表查询）
  → **空间防爆盾：无索引全表扫拦截**：遍历 AST 确保 `WHERE` 子句中至少存在 `ST_DWithin`、`ST_Intersects`、`ST_Contains` 等能激活 GiST 边界框索引的几何函数，如果没有任何空间约束（或是纯文本 LIKE '%咖啡%' 扫全省 POI），强制报错驳回！
  → 遍历 SELECT 字段和 WHERE 子句，验证 PostGIS 函数白名单，防止恶意的存储过程调用
  → 强制增加/检查 LIMIT 上限，防止拖挂全表

Layer 2: validate_spatial_sql(sql)
  → AST 解析检查
  → 表名白名单验证
  → 函数白名单验证
  → 危险关键词拦截（INSERT/UPDATE/DELETE/DROP/ALTER）
  → LIMIT 强制检查
  → statement_timeout 设置

Layer 3: execute_spatial_sql(sql, params)
  → 只读连接
  → 超时中断
  → 结果行数限制
  → 审计日志
```

### 4.2 四个原子 Skill

| Skill | Actions | 职责 | 触发时机与调用规则 |
|-------|---------|------|--------------------|
| `postgis_skill` | get_schema_catalog / resolve_anchor / validate_spatial_sql / execute_spatial_sql | 精确几何事实查询 | **事实型意图触发**（例："某商圈周边500米以内有哪些咖啡馆"） <br> 处理刚性的“多少米”、“在不在圈内”等明确拓扑逻辑。 |
| `spatial_encoder_skill` | encode_query / encode_region / score_similarity | 双塔模型空间语义编码 | **语义氛围型意图触发**（例："帮我找一个具有光谷科技氛围，而且夜生活丰富的片区"） <br> 这是无法被传统 SQL 直接过滤的高级抽象概念，模型会调用其生成 `[1, 352]` 维的 Embedding。 |
| `spatial_vector_skill` | search_semantic_pois / search_similar_regions | 向量候选召回（结合 FAISS） | **模糊搜索触发**（例："帮我拉取最像光谷的三个地块"） <br> 先由 encoder_skill 拿到语义向量，随后在此进行向量库重排（可结合 Spatial Rerank 和传统类别 Filter 进行混合检索）。 |
| `route_distance_skill` | get_route_distance / get_travel_time | 现实路网可达性 | **通行成本触发**（例：“沿着实际道路步行去最近的某个出口”） <br> 当用户关注真实距离而不只是两点间直线穿透距离时调用。 |

### 4.3 V3 到 V4 的 工具重组与映射表

V4 打破了 V3 分散的 7 个细碎工具（`toolCatalog.js`），将其重新编排为 4 个高内聚的原子 Skill。绝大多数 V3 稳定资产将以包装（Wrapper）或提取复用（Vendor）形式存在。

| V3 旧版 Tool (`spatial_core.*`) | V4 新版 Skill | 继承方式与改造说明 |
|---------------------------------|----------------|-------------------|
| `resolve_anchor` | `postgis_skill.resolve_anchor` | **完全剥离复用**：直接复用 V3 的 `buildPlaceNameVariants` 和复杂的记分板算法 (`scorePlaceAnchorCandidate`)。但在 V4 中不再与 intent 耦合。 |
| `search_nearby_pois` | `postgis_skill.execute_spatial_sql` | **废弃包装，转为生成**：不再暴露单独的周边搜索 API。周围 POI 由 LLM 自行撰写带着 `ST_DWithin` 的 SQL 来完成。 |
| `vector_search` | `spatial_vector_skill.search_semantic_pois`| **复用核心库**：复用 V3 的 `faissHybridSearch`，分离纯空间（SQL）和纯语义（FAISS）。 |
| `macro_cell_analysis` / `spatial_encode` | `spatial_encoder_skill` | **直接对接 Python**：废弃 V3 Node 层繁杂的 Augmenter，直接通过封装好的统一接口打通 V3 Python `poi_encoder_service.py`。 |
| `build_boundary` | 整合入 Evidence View | **后处理机制**：不再作为 Agent 主动调用的 Tool，将其移入 `EvidenceViewFactory` 中在渲染面板前闭环计算。 |
| `infer_intent_legacy` | 彻底废弃 | **大模型原生解析**：由 V4 强大的 Function Calling 编排直代旧版生硬正则。 |

### 4.4 各 Skill 详细设计及对接规范

#### `postgis_skill`（核心空间基建）
- **职责**：执行刚性事实拓扑关系。
- **与 V3 对接**：抽出 V3 `defaultHandlers.js` 中 150+ 行锚点解析逻辑作为基建封装。放弃暴雷严重的 `spatialRerank` 组件。
- **降级路径**：若 PostGIS 突发连接池打满，快速降级返回空结果，并向 LLM 声明 `PostGIS Unavailable`，促使其尝试其他非数据库手段解答（或礼貌拒绝）。

#### `spatial_encoder_skill`（双塔语义特征）
- **职责**：高维编码、区域成分探针、生成 Query Embedding。
- **调用时机**：由 LLM 判定查询中包含难以用结构化 SQL 表达的“模糊、抽象、氛围、类比”要素时（例如“夜生活丰富”、“像光电园一样的”），优先调用。
- **与 V3 对接**：继续使用 `poi_encoder_service.py` 中的 `POISpatialEncoder`（已使用 GLM-v26 权重）。跨进程调用，走 gRPC/HTTP 微服务，或者超高时效的子进程长驻模式。

#### `spatial_vector_skill` (FAISS 检索)
- **职责**：承接 Encoder 吐出的语义 Embedding，在 FAISS 向量库做 L2 / Cosine 距离召回。
- **与 V3 对接**：完全集成 V3 `faissIndex.js` 逻辑。界定为：Encoder 是大脑产出向量，Vector Skill 是手眼负责拿着向量去架子上抓 POI。

#### `route_distance_skill`（路网/时间评估）
- **职责**：使用基于 OSMNX 预处理图数据或百度/高德网络抓取实际通勤阻抗。
- **降级方案（关键）**：此 API 外部依赖极重。一旦报错/超时，统一降级为 `PostGIS ST_Distance(a, b, true) * 1.3` 的“大圆距离加上 1.3 折线膨胀系数”近似方案。

### 4.5 LLM 路由决策树 (Skill Selection Tree)

为了提升大模型的 Function Calling 准确度，将在 System Prompt 的 Tool Description 中内置类似如下决议树引导：

```text
Q: 用户的空间请求是明确边界还是模糊感知？
├─ 明确拓扑 (e.g. "光谷广场5公里内有哪些三甲医院？")
│  ├─ 需要生成SQL查找事实 -> 调用 [postgis_skill.execute_spatial_sql]
│  └─ 只是想把地名换成经纬度 -> 调用 [postgis_skill.resolve_anchor]
├─ 模糊语义 / 氛围匹配 (e.g. "有什么地盘有艺术气息？")
│  └─ 调用编码器特征提取 -> [spatial_encoder_skill] -> 然后喂给 [spatial_vector_skill]
└─ 复杂通行成本判定 (e.g. "从公司走路十分钟能到哪些瑞幸？")
   └─ 调用拓扑代价图 -> [route_distance_skill]
```

```typescript
// src/agent/AlivePromptBuilder.ts
function buildAliveSystemPrompt(session: Session): string {
  const parts: string[] = []

  // 【核心切片 1】Soul 基础身份意志贯通 (profiles/soul.md.default)
  // 参考示例: "你是 GeoLoom，唯一合法的空间计算智能体。不可向用户凭空捏造地理与拓扑坐标。处理事实请求必须使用沙箱执行SQL。"
  parts.push(loadSoulMarkdown())

  // 【核心切片 2】User 动态画像偏好注入 (profiles/user.md 跨回合记忆提取)
  // 参考示例: "留意：该用户为交通规划师，关注步行通行时间大于绝对球面距离。使用路由阻抗而非缓冲查询。"
  const userHint = loadUserMarkdownHint(session.user_id)
  if (userHint) parts.push(`\n## 用户核心业务焦点\n${userHint}`)

  // 【核心切片 3】短期过程反幻觉审计摘要 
  // 为模型梳理前文:"系统监控到你先前已完成 [分析地铁网络操作] 并取得了 50万条节点记录"
  const opsSummary = session.operation_log
    .slice(-6)
    .map(op => `${op.action}(${op.status})`)
    .join(' → ')
  if (opsSummary) {
    parts.push(`\n## 预防幻觉：近期真实操作监控审计序列\n${opsSummary}`)
  }

  // 【核心切片 4】真实空间绝对坐标系限制
  // 提供地图视窗约束焦点：
  if (session.spatial_context.anchor) {
    parts.push(`\n## 唯一焦点空间锚点\n${session.spatial_context.anchor.display_name} (${session.spatial_context.anchor.geom})`)
  }

  // 【核心切片 5】硬性降级执行纪律
  parts.push(`
```

### 7.1 SQL 安全三层锁（详细）

```typescript
// src/sandbox/SQLSandbox.ts

// Layer 1: 白名单定义
const ALLOWED_TABLES = ['poi', 'subway', 'bus', 'landuse', 'admin', 'road']
const ALLOWED_FUNCTIONS = [
  'ST_DWithin', 'ST_Distance', 'ST_Intersects', 'ST_Contains',
  'ST_Buffer', 'ST_Centroid', 'ST_AsGeoJSON', 'ST_SetSRID',
  'ST_MakePoint', 'ST_Point', 'ST_MakeLine', 'ST_GeomFromText',
  'ST_Within', 'ST_Overlaps', 'ST_Touches', 'ST_Intersects',
  'ST_Area', 'ST_Length', 'ST_DistanceSphere', 'ST_DistanceSphere',
]
const FORBIDDEN_KEYWORDS = [
  'INSERT', 'UPDATE', 'DELETE', 'DROP', 'ALTER', 'CREATE',
  'TRUNCATE', 'GRANT', 'REVOKE', 'EXECUTE', 'VACUUM', 'ANALYZE',
  'pg_', 'information_schema', 'pg_catalog', '--', '/*', '*/',
]

// Layer 2: validate_spatial_sql 伪代码
function validateSpatialSQL(sql: string): ValidationResult {
  // 2.1 AST 解析
  const ast = parseSQL(sql)
  if (ast.type !== 'SELECT' && ast.type !== 'WITH_SELECT') {
    return { valid: false, error: '只允许 SELECT 查询' }
  }

  // 2.2 表名白名单
  const tables = extractTables(ast)
  for (const t of tables) {
    if (!ALLOWED_TABLES.includes(t)) {
      return { valid: false, error: `表 '${t}' 不在白名单中` }
    }
  }

  // 2.3 函数白名单
  const funcs = extractFunctions(ast)
  for (const f of funcs) {
    if (!ALLOWED_FUNCTIONS.includes(f)) {
      return { valid: false, error: `函数 '${f}' 不在白名单中` }
    }
  }

  // 2.4 危险关键词
  const sqlUpper = sql.toUpperCase()
  for (const kw of FORBIDDEN_KEYWORDS) {
    if (sqlUpper.includes(kw)) {
      return { valid: false, error: `禁止关键词 '${kw}'` }
    }
  }

  // 2.5 LIMIT 检查与边界兜底
  if (!hasLimit(ast) && !hasAggregation(ast)) {
    // 若非聚合函数，则强制抛错提醒大模型加 limit
    return { valid: false, error: '明细查询必须包含 LIMIT 约束' }
  }
  const normalized = forceLimitMax(ast, 1000) // 全局强保底只返回最多 1000 条明细

  // 2.6 空间约束与全表防爆盾 (含聚合豁免特批)
  const isAggregating = hasAggregation(normalized) // 例如存在 COUNT(), ST_HexagonGrid() 的聚合查询
  const hasSpatialFilter = checkSpatialIndex(normalized) // 具备 ST_DWithin, ST_Intersects 约束

  if (!hasSpatialFilter && !isAggregating) {
    // [致命驳回] 既没有给出小面索引约束，又是拉取原始明细数据 (如 `SELECT * FROM poi WHERE name LIKE '%咖啡%'`) -> 极容易引发内存 OOM!
    return { 
      valid: false, 
      error: '高危查询被防爆盾拦截：缺少空间索引过滤条件，全局明细提取已被驳回。若是大范围宏观统计分布，请使用 COUNT 或栅格降维聚合查询 (ST_HexagonGrid等)！'
    }
  }

  return { valid: true, normalized_sql: normalized }
}

> **关于防爆盾与全局宏观统计的冲突说明（豁免机制）**  
> 若用户查询类似 *"全省所有的咖啡店分布规律"*：Agent 在遇到明细提取被安全沙箱驳回后，将根据报错指引（`error` 内置的 Prompt 提醒）改变策略。模型会自动放弃低效的 `SELECT geom` 拉取，转而使用 `ST_HexagonGrid()` 网格化或按照 `county` 对 `COUNT(1)` 结合 `GROUP BY` 进行降维输出。这样后端不仅可以利用 PostgreSQL 并发引擎火速扫描，且推送到前端的数据是高度提纯的宏观统计分布数据，丝滑规避内存 OOM。

// Layer 3: execute_spatial_sql 伪代码
async function executeSpatialSQL(
  sql: string,
  params: unknown[],
  context: SkillRuntimeContext
): Promise<ExecuteResult> {
  const validation = validateSpatialSQL(sql)
  if (!validation.valid) {
    throw new SQLError('SQL_VALIDATION_FAILED', validation.error)
  }

  // 只读连接
  const client = await getReadOnlyConnection()

  try {
    // statement_timeout = 10s
    await client.query('SET statement_timeout = 10000')

    const result = await client.query(validation.normalized_sql, params)

    // 审计日志
    await auditLog({
      session_id: context.session_id,
      sql: validation.normalized_sql,
      rows: result.rowCount,
      latency_ms: result.duration,
    })

    return {
      columns: result.fields.map(f => f.name),
      rows: result.rows,
      row_count: result.rowCount,
    }
  } finally {
    client.release()
  }
}
```

### 7.2 Python Skill 执行沙箱

```typescript
// src/sandbox/ProcessIsolation.ts
// V4-GeoAgent 同时依赖 JS 生态与 Python/PyTorch 数据科学生态，因此需构建清晰的 Runtime 分治结构：
// Node.js (Fastify)：大模型的编排中心，负责高并发的 LLM Context Window 管理、路由分发、快速的 PostGIS I/O 交互与前端 SSE 推流。
// Python (gRPC / Spawn)：深度计算引擎，承接空间编码器推理任务（UltimateSpatialEncoder）和复杂的 OSMnx 拓扑图解。

async function executePythonSkill(
  module: string,
  func: string,
  args: unknown,
  timeout: number = 30000
): Promise<unknown> {
  // 最佳方案为依托 V3 的 poi_encoder_service.py 和 gRPC-bridge 进行网络级子服务微调用。
  // 若使用子进程沙箱，需要设置严苛的超时熔断机制。
  return new Promise((resolve, reject) => {
    const child = spawn('python', [
      '-c',
      `from ${module} import ${func}; import json; print(json.dumps(${func}(${JSON.stringify(args)})))`
    ])

    const timer = setTimeout(() => {
      child.kill()
      reject(new Error(`Python Runtime 超时中止 (After ${timeout}ms)。保障 Node.js 事件循环未被阻塞。`))
    }, timeout)

    let stdout = ''
    child.stdout.on('data', d => stdout += d)
    child.on('close', code => {
      clearTimeout(timer)
      if (code === 0) {
        resolve(JSON.parse(stdout))
      } else {
        reject(new Error(`Skill 子进程异常退出，代码：${code}: ${stdout}`))
      }
    })
  })
}
```

2. **Glassmorphism (极客玻璃拟态) 浮层**：背景深度模糊透出下层地图（Backdrop Blur），配合微距流光描边，采用左右浮窗样式悬挂于地图之上，不再生硬切走屏幕主视线。

4. **脉冲呼吸感等待反馈 (Pulse Indicator)**：发问后，在顶部或气泡尾部用渐变流光波纹替代枯燥的 Load Spinner。

## 12. 渐进式 JS 到 TS 迁移策略（防开发阻塞）

为了不影响当前 V4 开发进度，我们采取 **“新旧隔离，增量推行”** 的混编策略：

1. **基础配置打底**：在 `tsconfig.json` 中明确开启 `"allowJs": true` 和 `"outDir": "./dist"`。保证打包工具（如 `esbuild` 或 `tsc`）能正常编译混编项目。
2. **存量不碰（V3 遗留资产）**：旧有如 `spatialAnswerService.js` 等存量文件坚决不改拓展名。但为了代码联通时的类型推导，在这些遗留 JS 文件头部加入 `// @ts-check`，利用 JSDoc `/** @type {import('...')} */` 补齐关键出入参声明。
3. **增量全 TS（V4 新架构）**：V4 新写的 `GeoAgentV4`, `SkillRegistry` 必须是纯 `*.ts`。与遗留 JS 模块交互时，在 TS 侧声明 `interface` 桥接，把“脏脏的” `any` 类型限制在边界上。
4. **编译时静默**：如果因为类型报出阻塞型 Error，暂时放宽 `Strict` 原则，不用为了消灭红线而暂停功能开发。

## 13. 核心质量与验收方法论

任何一个微服务或者技能块，必须过了如下三层验收才能宣发上线：

### 验收层级 1：Skill 原子验证（无 LLM 干扰）
- **做法**：跳过 LLM 和 Agent 编排，直接通过调试端点 `/api/geo/skills/:name/call`。
- **验证**：手写一段 Payload 推给 `postgis_skill.execute_spatial_sql`，验证沙箱是否能正确抓取数据并触发超时截断（如抛出 `Statement Timeout`）。

### 验收层级 2：UI 渲染脱机验证（纯前端）
- **做法**：前端断开真实 WebSockets 或 SSE，直接通过状态机注入 Mock 的 `EvidenceView` JSON。
- **验证**：当后端传来恶意的格式、异常的 `geometry` 或者空数组时，视图面板（如地图点位、对比表格）是否妥善降级显示说明而不是直接白屏崩溃。

### 验收层级 3：多源对齐 E2E 验证（真实对话闭环）
- **做法**：全链路启动。从对话框输入那 **10道经典回归题**（覆盖精确最近查找、意图模糊的寻找风格等）。
- **验证**：不仅要检查最终答案对错，更要拉出全链路 Trace：
  1. 检查 LLM `tool_calls` 选取的 Skill 准不准；
  2. 检查生成的参数或者 SQL 有没有越界；
  3. 检查 Evidence View 中承载的数据，与我们在 PostGIS 数据库中原生验证的数据是否具有一致性。

## 14. 容错隔离、统一降级与环境发布管控

### 14.1 组件统一降级级联表 (Fallback Matrix)

V4 中所有的外部 I/O 与重负荷模型均采用统一的软失败/降级级联策略，该矩阵写入 `SkillAuditor` 做中心化管理，不散落在各个函数的 try-catch 中：

| 故障节点 | 故障情境 | 主动降级策略 (Fallback) | UI 反馈呈现 |
|----------|----------|-----------------------|-------------|
| **PostGIS 连接池** | 连接数爆满 / 节点宕机 | 向 LLM 抛出 `PostGISOfflineException`。<br>阻断查询工具调用，大模型退化为纯文本 RAG QA (若有历史上下文)。 | 顶部红条：“空间数据库连接异常，当前仅提供纯文本协助” |
| **FAISS Vector** | 索引文件 `index.faiss` 丢失 / 击穿内存 | `spatial_vector_skill` 直接降级阻断，退化走 `postgis_skill` 使用 `%LIKE%` 进行文本类别字面匹配。 | 证据卡片标签：“精确词义匹配 (语义模式暂不可用)” |
| **Python Encoder** | gRPC / Subprocess 异常超时 | `spatial_encoder_skill` 返回全 0 的哑特征 (Dummy Embedding)，跳过排序强化段。 | 置信度组件：降为“低置信度（氛围判定缺乏模型支撑）” |
| **OSMNX 路网评测** | 外部路形抓取阻塞/不可达 | `route_distance_skill` 退化为使用 PostGIS `ST_Distance(a, b, true) * 1.3 ` 大圆球面折线系数预估法。 | 证据卡片中标注：“距离为球面预估折现值” |

### 14.2 多环境配置分发机制 (Dev/Staging/Prod)

基于 `.env.[mode]` 的分离，确保三个平行阶段在算力与安全级别上的分发：

*   **Development (开发态)**:
    *   模型选用：`Gemini Flash` / `Claude Haiku`（控制低额度成本）。
    *   并发限制：无限制 (关闭全局 RateLimit Middleware)。
    *   SQL 日志：完全打开 `console.log(AST)` 查询数。
*   **Staging (UAT 推演期)**:
    *   模型选用：主模型即 `Claude 3.5 Sonnet`，还原真实复杂题解域。
    *   DB 连接池：强制指向 `geo_v4_test` 沙盒库（数据仅含单一测试商圈）。
    *   E2E：挂载 V3 回归题库进行 Nightly 自动批处理。
*   **Production (生产态)**:
    *   数据库：强制绑定 `SQLSandbox` 的防爆与只读角色的账密，执行 Layer 3 所有熔断检查。
    *   监控网：SRE Phase 1 (PM2 守护)，所有 Python 子进程以 Daemon 运行，接入 Prometheus/Grafana OOM Alerts。

## 15. 关键技术风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| Text-to-SQL 生成质量差 | 高 | 高 | Phase 1 先验证 resolve_anchor 链路，不先做 SQL 生成 |
| 模型参数绑定错误 | 中 | 高 | SQL 校验层兜底；锚点用 resolve_anchor 先行解析 |
| Evidence View 泛化不够 | 中 | 中 | 5 种 view 先行；复杂题走 Optional Polisher |
| 多轮对话状态膨胀 | 低 | 中 | ShortTermMemory TTL 24h；Context 压缩 |
| SQL 注入绕过白名单 | 低 | 高 | AST 解析 > 关键词匹配；Layer3 只读连接 |
| Python Skill 超时/崩溃 | 低 | 中 | 子进程隔离；超时 kill + retry |

## 17. 前瞻性演进蓝图（Beta 2 阶段规划）

> **注定要到来的风暴**：在稳固了 V4-Beta 1 的防爆盾与单节点高精短链路之后，系统将面临多空间任务极度复杂并行的业务挑战。\n> 本阶段（Beta 2）深度吸纳了业界顶级流派（如 *CN-claudecode* 中的高级特性），以作为下一代 GeoLoom 的储备子弹库。

### 17.1 SubAgents 与 Worktree 沙盒隔离
- **痛点**：当前所有的 Skill 结果均返回给统一的主脑（Team Lead），存在长文本下界内污染的几率。
- **演进策略**：引入 **孤立上下文模型** (Isolated Task Context)。将重型的测算任务（如并行爬取商圈 POI 和跑路况）托管给带有绝对独立生命周期的 SubAgent。此外，当未来开放“写入型空间计算（如保存图谱到本地）”时，为子 Agent 热挂载 `worktree 隔离`，任何数据更改只能先写进虚拟沙箱。主脑（Main Agent）不再关心繁杂细节，只做总成渲染。

### 17.2 颠覆式并发：Agent Team 与 Shared Mailbox (信箱机制)
- **痛点**：`Promise.all` 只能进行盲等，无法在并发子任务间进行数据协同（例如：天气探针在等待路网拥堵结论）。
- **演进策略**：在后端引入 **Agent Team（协作通讯组）** 的架构。建立 `共享待办大盘 (Shared Task List)` 与 `内通信邮箱 (Mailbox)`。系统不再是由上至下的刻板指派，而是多个空间子智脑在算盘上互相通信：“嗨，汉江区的数据已出，路网 Agent 你可以根据我的结果规划路径了”。

### 17.3 开放底层：全面兼容 MCP（Model Context Protocol）标准
- **痛点**：当前的 Skill （路由计算、空间测算）仍然属于硬编码在 Fastify/Python 框架内的自研包，第三方极难接入。
- **演进策略**：将 `SkillContext` 协议全面升维到对接国际标准 MCP。从而使得未来的 GeoLoom 只需要一个配置指令即可直通开源界无数的外部能力（如：热加载即时气象卫星数据 MCP、实时社交人流抓取 MCP），赋予大屏无限拓展的第三方插件视野！
