# 普适性 GEO AGENT 重构执行文档

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 把当前 V3 从“局部题型优化 + 大量规则兜底”的空间问答系统，重构成“LLM 负责理解用户空间/语义意图，空间系统负责拿证据，回答层只负责基于证据反馈用户”的普适性 GEO AGENT。

**Architecture:** 用户输入先被翻译成通用的 `intent_spec`，再由 `spatial_core` 按 `intent_spec` 调 PostGIS、POI 编码器、town/cell 编码器去拿证据；证据被整理为统一的 `evidence_profile` 和 `synthesis_brief` 后交给回答层。重点不是继续补规则，而是建立“意图 -> 证据 -> 回答”的稳定中间层，让不同空间问题都走同一套机制。

**Tech Stack:** Node.js(Fastify/Vitest) + Python Spatial Encoder Service + PostGIS + pgvector + Ollama/LM Studio + SSE

## 一、主体思想（必须无条件服从）

这是本次重构的最高原则，后续实施者不能偏离：

1. **系统的核心不是写规则，而是理解用户当前的空间/语义意图。**
   不是“用户问了哪个固定句子”，而是“用户这一问真正关心什么空间对象、什么空间范围、什么聚合方式、什么排序目标”。

2. **重要信息是否保留，必须由当前意图决定。**
   例如：
   - 问“地铁站”时，公交站是噪声；
   - 问“公交站”时，地铁站是噪声；
   - 问“公共交通”时，地铁站和公交站都必须保留；
   - 问“区域概览”时，局部门店往往不是主角，宏观业态主轴才是主角。

3. **LLM 不负责记住空间事实，LLM 负责把问题翻译成可执行意图。**
   空间事实始终来自：
   - PostGIS
   - POI 编码器
   - Town/Cell 编码器
   - 几何/边界构建能力

4. **回答层不能成为新的规则堆。**
   `fallback` 只是安全网，不是主驾驶；不能继续通过堆模板来伪装“智能”。

5. **目标是普适性，不是单题分数。**
   不能再围着：
   - `请概览武汉大学附近的空间结构和业态分布`
   - `武汉大学附近有哪些咖啡店`
   这种固定问法做专项打磨并自我感动。

## 二、必须避开的两个大雷区

### 雷区 1：继续创造更多条例规范

以下实现方式一律视为失败实现：

1. 根据原始 query 字面关键词继续长越来越多的 if/else。
2. 为某个任务类型手写一堆特供过滤器。
3. 在 `rules_line`、`supportEvidenceUtils`、`spatialAnswerService` 中继续堆新规则。
4. 通过“更多 fallback 模板”掩盖底层意图理解和证据选择能力不足。

**判断标准：**
如果一段代码的核心逻辑是“因为用户说了某个词，所以手写保留/剔除某类点”，且它不是低层数据清洗规则，那么它大概率就是雷区代码。

### 雷区 2：继续围绕单题做专项优化

以下行为一律视为方向跑偏：

1. 针对某一个 query 把答案打磨得很好看。
2. 针对某一类校园概览题写特供代表点筛选。
3. 看到某个回归题不够漂亮，就继续在该题附近补题型专用逻辑。

**判断标准：**
如果一个优化不能自然迁移到：
- 锚点附近查询
- 几何圈选查询
- 多锚点比较
- 交通类设施查询
- 宏观概览

那就不是本次要的优化。

## 三、真正要做的目标架构

### 目标总链路

1. 用户提问 / 画圈 / 指定半径 / 指定多个锚点
2. LLM 将输入翻译成通用 `intent_spec`
3. `planner_line` 根据 `intent_spec` 生成 `execution_plan`
4. `spatial_core` 执行 plan，分别向：
   - PostGIS
   - POI 编码器
   - Town/Cell 编码器
   - 几何能力
   拿证据
5. 后端将证据整理成：
   - `evidence_profile`
   - `synthesis_brief`
6. 回答层基于 `synthesis_brief` 生成最终回答
7. 若 LLM 输出污染、失真或越界，则退回极简 `fallback`

### 关键原则

1. **意图层要通用，不按题型硬编码。**
2. **执行层要工具化，不按问句特供。**
3. **证据层要中间化，不直接把原始 JSON 扔给回答层。**
4. **回答层要轻，不再成为逻辑主战场。**

## 四、第一性原理下的模块职责

### 1. `intent_spec` 层

这是本次重构的核心新层。

它负责回答以下问题：

1. 用户当前关心的对象是什么？
   - 地铁站
   - 公交车站
   - 公共交通
   - 餐饮配套
   - 区域主轴
   - 商超
   - 医疗设施

2. 用户当前关心的空间范围是什么？
   - 锚点附近
   - 1km/2km
   - 画圈 polygon
   - 双锚点比较
   - 自定义 geometry

3. 用户当前关心的聚合方式是什么？
   - lookup
   - overview
   - comparison
   - gap
   - suitability

4. 用户当前希望保留/弱化/剔除什么？
   - 保留对象
   - 允许共现对象
   - 噪声对象
   - 代表点偏好

**⚠️ 当前文档必须明确：如果 `intent_spec` 只停留在以上自然语言描述层面，它仍然不够。**

如果 `intent_spec` 最终只包含：
- `target_entities`
- `spatial_scope`
- `aggregation_mode`
- `ranking_objective`

那么系统还是会退回到：
- 靠 query 关键词命中规则
- 靠题型特供筛选器
- 靠 fallback 模板补洞

这不符合本次重构目标。

#### `intent_spec` 必须包含的最小字段集

以下字段是**最低不可再删减**的版本：

```json
{
  "task_type": "lookup | overview | comparison | gap | suitability",
  "spatial_scope": {
    "mode": "anchor_radius | geometry | dual_anchor | corridor | region",
    "anchor_refs": [],
    "geometry_ref": null,
    "radius_m": null
  },
  "semantic_focus_terms": [],
  "target_entities": [
    {
      "type": "poi | transport_node | region_feature | category_bucket",
      "value": "地铁站"
    }
  ],
  "include_entities": [],
  "exclude_entities": [],
  "aggregation_mode": "list | distribution | summary | comparison",
  "ranking_objective": "distance | semantic_relevance | representativeness | completeness",
  "completeness": "top_k | exhaustive",
  "answer_mode": "direct_list | area_portrait | contrast | recommendation",
  "needs_clarification": false,
  "missing_inputs": []
}
```

#### 必须补上的增强字段

为了真正支持“问什么，就围绕什么拿证据”，还必须增加以下增强字段：

```json
{
  "entity_resolution": {
    "merge_station_exits": true,
    "merge_same_poi": true,
    "category_level": "main | sub | bucket"
  },
  "spatial_relation": {
    "relation": "nearby | inside | around | between | compare",
    "distance_constraint_m": 1000,
    "geometry_constraint": "strict_inside | centroid_inside | intersects"
  },
  "evidence_policy": {
    "must_use_sources": ["postgis", "poi_encoder"],
    "prefer_sources": ["town_encoder"],
    "forbid_sources": [],
    "macro_required": false,
    "micro_required": true
  },
  "representation_policy": {
    "representative_example_count": 3,
    "allow_local_shop_as_region_representative": false,
    "prefer_public_civic_examples": true
  },
  "uncertainty_policy": {
    "allow_estimation": false,
    "require_confidence_note_when_sparse": true
  },
  "output_contract": {
    "must_include": [],
    "must_avoid": ["unverified_claims"],
    "tone": "concise | natural | analytical"
  }
}
```

#### 为什么这些字段不能少

以下差异必须由 `intent_spec` 表达，而不能继续靠写死规则：

1. `湖北大学附近 1km 内所有公交车站`
   - `target_entities = 公交车站`
   - `completeness = exhaustive`
   - `entity_resolution.merge_station_exits = true`
   - 如果 `target_entities` 已足够明确，不要求机械补 `exclude_entities = [地铁站]`

2. `湖北大学附近的公共交通`
   - `semantic_focus_terms = [公共交通]`
   - `target_entities = [地铁站, 公交车站]`
   - 不能把“公共交通”直接停留在抽象层，也不能把公交或地铁写死为噪声
   - `aggregation_mode` 很可能是 `summary`

3. `请概览武汉大学附近的空间结构和业态分布`
   - `aggregation_mode = summary`
   - `answer_mode = area_portrait`
   - `evidence_policy.macro_required = true`
   - `representation_policy.allow_local_shop_as_region_representative = false`

4. `这个圈里的业态分布如何`
   - `spatial_scope.mode = geometry`
   - `geometry_ref` 必填
   - `aggregation_mode = distribution`
   - 不应退回到锚点特供逻辑

#### 本次执行的明确要求

执行者不能把 `intent_spec` 理解成“又一个 query 分类器”。

`intent_spec` 的真正作用是：

1. 描述当前问题要看什么对象
2. 描述当前问题的空间边界
3. 描述当前问题的语义焦点
4. 描述当前问题允许哪些共现对象
5. 描述当前问题哪些对象是噪声
6. 描述当前问题需要微观还是宏观证据
7. 描述当前问题最后答案要组织成什么样
8. 当输入不足时，明确要求补充什么，而不是继续脑补

只有做到这一点，后面：
- 地铁
- 公交
- 公共交通
- 区域概览
- 画圈查询
- 多锚点比较

才可能走同一套机制，而不是继续写题型特供规则。

#### `intent_spec` 的生成来源与输入模式（必须写死）

执行者必须明确区分三类输入来源，不能把它们强行塞进同一个“文本关键词解析器”：

1. **自然语言输入**
   - 例如：
     - `湖北大学附近 1km 内所有公交车站`
     - `请概览武汉大学附近的空间结构和业态分布`
   - 处理方式：
     - 由 LLM 或轻量 parser 先生成 `intent_spec`

2. **半结构化输入**
   - 例如：
     - 已知 `anchor`
     - 已知 `radius`
     - 已知 `category`
   - 处理方式：
     - 不要求重新走完整文本理解
     - 可直接组装 `intent_spec`

3. **结构化空间输入**
   - 例如：
     - polygon
     - bbox
     - draw tool 返回 geometry
   - 处理方式：
     - 直接写入 `intent_spec.spatial_scope`
     - 不允许退回“锚点特供解析”

**硬要求：**
- `intent_spec` 是系统主中间层，不是仅服务文本 query 的解析结果。
- 执行者如果继续做一个“大而全的 query 解析器”，而不是统一的 `intent_spec` 组装层，视为方向跑偏。

### 2. `spatial_core` 层

只负责提供空间事实，不负责理解用户原始问句。

职责：

1. `resolve_anchor`
2. `resolve_geometry`
3. `search_nearby_pois`
4. `search_inside_geometry`
5. `search_transport_nodes`
6. `macro_cell_analysis`
7. `build_boundary`
8. `vector_search`

**注意：**
这里的“过滤什么、保留什么”，不该再来自手写题型规则，而应该来自 `intent_spec`。

### 3. `evidence_profile` 层

把原始证据提炼成“当前问题真正关心的证据骨架”。

至少要包含：

1. `style`
2. `task_type`
3. `focus_terms`
4. `target_entities`
5. `transport_modalities`
6. `dominant_buckets`
7. `scene_tags`
8. `cell_mix`
9. `representative_examples`
10. `uncertainty`

### 4. `synthesis_brief` 层

这是喂给回答层的最终摘要，不再喂完整 evidence JSON。

它应该更像：

```json
{
  "anchor": "武汉大学",
  "style": "overview",
  "core_axes": ["教育服务", "生活服务", "餐饮配套"],
  "scene_tags": ["教育氛围", "居住社区"],
  "spatial_mix": ["公共类", "居住类"],
  "representative_examples": ["武汉大学万林艺术博物馆", "武汉大学珞珈文库", "武汉大学-新闻中心"],
  "constraints": ["不要把局部门店写成区域主轴", "不要把模糊边界写成精确边界"]
}
```

## 七、性能目标与非目标

### 本轮性能目标

1. **意图规格化**
   - 尽量控制在低延迟
   - 小模型 / 轻量 parser / 结构化输入直组装均可

2. **空间检索与证据选择**
   - 目标是 ms ~ 百ms 级
   - 重点优化：
     - PostGIS 空间过滤
     - 向量检索
     - 证据聚合

3. **回答生成**
   - 允许是低秒级
   - 优先流式与可降级

### 本轮明确非目标

1. **不是追求最终自然语言回答 ms 级**
   - 只要有 LLM 文本生成，通常就是百ms到秒级，不作为本轮验收要求

2. **不是把空间数据库直接微调进大模型**
   - 这会带来：
     - 时效性问题
     - 精确查询问题
     - 维护成本问题

3. **不是为了快继续堆模板或规则**
   - 这会牺牲普适性，反而破坏本轮目标

### 本轮推荐形态

1. **快路径**
   - `intent_spec`
   - 空间检索
   - 证据骨架
   - fallback / 结构化返回

2. **慢路径**
   - 在快路径证据之上
   - instruct 模型做自然语言润色

这意味着本轮真正要优化的是：
- 证据拿得快
- 证据拿得准

## 十二、最终判断标准

如果执行完以后出现以下迹象，说明方向仍然错了：

1. 还是不断增加 query-specific 规则
2. 还是通过 fallback 模板掩盖证据选择问题
3. 还是围绕某一道题做专项美容
4. `rules_line` 代码量不降反升

如果执行完以后出现以下迹象，说明方向开始对了：

1. 同一套 `intent_spec` 可以处理地铁、公交、公共交通、概览、圈选查询
2. 证据选择越来越由意图驱动，而不是题型驱动
3. 回答越来越像普通 LLM，但仍然证据受控
4. 旧规则代码明显减少
