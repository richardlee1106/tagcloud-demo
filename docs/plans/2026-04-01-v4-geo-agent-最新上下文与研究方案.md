## 2. 项目背景

当前项目并不是一个普通的“附近有什么”检索系统，而是在尝试做一个真正的 **空间 Agent**：

- 用户用自然语言提问
- 系统理解空间意图
- 系统调用 PostGIS、空间编码器、向量检索、路网能力去拿真实证据
- 系统把结果反馈给用户

项目当前已有的重要基础：

1. **PostGIS**
   - 提供精确几何与空间关系能力
   - 适合做最近、范围、包含、相交、聚合等“硬事实”

2. **空间编码器 / 双塔模型**
   - 提供“空间语义”能力
   - 适合做相似区域、模糊空间语义召回、空间语义匹配

3. **向量数据库 / 向量检索**
   - 提供候选召回能力
   - 适合做 coarse retrieval，再交给更精细的空间计算收敛结果

4. **现有 V3 Planner Line / Spatial Core / Retrieval 管线**
   - 已经有很多可复用能力
   - 但主链路设计方向存在问题

项目真正的目标不是“答对 10 个固定问题”，而是：

> 做一个面对千变万化空间自然语言问题，仍能稳定理解意图、调用工具、拿真实空间证据、再生成最终回答的 Agent。

## 3. V3 当前已经暴露的核心问题

这部分非常重要，因为它决定了为什么不能继续沿旧路修修补补。

### 3.1 V3 的主链路太长

V3 的典型链路是：

`用户问题 -> planner LLM -> 执行 -> answer LLM -> 最终文本`

问题在于：

1. planner LLM 常驻主链路
2. answer LLM 常驻主链路
3. 空间执行本身其实不慢，但两次 LLM 让整体响应很重

已知实测里，简单题的总耗时常常在 `30s ~ 40s`，主要慢点不在空间检索，而在 LLM 主链路。

### 3.2 V3 过度依赖“中间文书”

V3 本质上是：

- 先让 LLM 生成一份 planner / intent / brief
- 再由系统把这些中间结构层层加工
- 最后再让另一个 LLM 生成最终文本

这让系统非常像“先写计划，再写总结”，不像“一个真正会行动的 Agent”。

### 3.3 V3 的工具形态太像题型工作流

如果工具长得像：

- `macro_cell_analysis`
- `comparison_aggregation`
- `amenity_gap_analysis`

那么系统其实还是在走：

`问题分类 -> 固定工作流`

这类工具太重、太语义化，一旦用户问法变化、或者提出新的跨区域推理需求，泛化能力会急剧下降。

### 3.4 V3 在证据与表达之间仍有错位

已经暴露出来的例子包括：

1. 地铁题里“站级列表”和“出口级最近距离”混写
2. 配套题里说“餐饮配套明显”，但举例是娱乐点位

这说明：

- 原始空间证据未必有问题
- 真正的问题出在“证据组织方式”和“输出链路”

### 3.5 继续加规则会走回老路

如果继续：

1. 按关键词分类意图
2. 按题型分派预设工作流
3. 用更多 fallback 模板补洞

那系统只会越来越像规则堆，而不是 Agent。

## 4. 最新意图：我们到底要做什么

经过讨论后，当前最新共识如下：

### 4.1 不再把“微调小模型”当第一主线

小模型微调仍然可能有价值，但它不应该是第一步。

原因：

1. 如果架构还是错的，微调只是在错误架构上省成本
2. 如果工具还是重工具，微调只是在背固定轨迹
3. 这不符合“真 Agent”的方向

### 4.2 第一主线改为“强模型 + 原子空间 Skills + Function Calling”

当前最值得验证的主线是：

1. 让强模型做“大脑”
2. 让空间能力通过原子化 skills 暴露出来
3. 让模型用 function calling 现场组合这些能力
4. 真实空间证据回传给模型
5. 模型再决定下一步，直到输出结果

### 4.3 真正的难点，不是空间编码器本身

当前最大的难点是：

> 如何让大模型在理解用户自然语言空间意图的基础上，学会调用空间工具、调用空间编码器、调用 PostGIS，去做一个真正的空间 Agent。

换句话说，难点是：

- `自然语言 -> 空间行动`

而不是：

- `自然语言 -> 再生成一份 planner JSON`

### 4.4 当前更接近正确方向的关键词

以下方向是当前主线关键词：

1. `Text-to-Spatial-SQL`
2. `Function Calling`
3. `Atomic Skills`
4. `Workflow Orchestration`
5. `Evidence-backed Answering`

## 5. 当前明确放弃或后移的方向

为了防止另一个窗口 AI 再走回旧线，这里明确写死：

### 5.1 当前不建议优先做的事

1. 优先训练 `Qwen3-1.7B` 当主控制脑
2. 继续围绕 `intent_spec -> heavy tool routing` 设计主架构
3. 封装大量“配套分析 / 比较分析 / 区域画像”这类重工具
4. 把问题拆成越来越多的预定义意图
5. 再花大量时间优化 V3 的 planner prompt / answer prompt

### 5.2 为什么这些方向现在要后移

因为它们都容易回到同一个问题：

> 系统看起来像智能，但本质上还是“意图分类 + 固定工作流”。

## 6. 当前建议采用的 V4 总体架构

### 6.1 一句话版本

V4 不是：

`自然语言 -> 分类成某种空间题型 -> 路由到固定工具链`

而是：

`自然语言 -> 强模型理解与编排 -> 调用原子空间 skills -> 返回真实证据 -> 继续推理 -> 输出答案`

### 6.2 总体流程图

```text
用户自然语言问题
  -> 强模型（大脑）
  -> 读取 schema / tool spec / skill contract
  -> 决定调用 1~N 个原子空间 skills
  -> 本地执行真实空间工具
  -> 返回结构化结果 / GeoJSON / 表格数据 / 统计结果
  -> 强模型继续决定是否需要二次调用
  -> 产出最终回答或结构化视图
```

### 6.3 这个架构与旧架构的本质差异

旧架构更像：

- 先决定题型
- 再走预制流程

新架构更像：

- 先理解真实目标
- 再现场决定调用哪些底层能力

这才更配得上“Agent”。

## 7. Skill 设计原则：一定要原子化，不要重工具化

这是当前最重要的技术原则之一。

### 7.1 错误方向：重工具

以下这类工具虽然好理解，但不适合做 Agent 主能力：

- `analyze_amenity_gap(area)`
- `compare_regions(a, b)`
- `macro_cell_analysis(anchor)`
- `overview_neighborhood(anchor)`

问题：

1. 太依赖预设题型
2. 泛化差
3. 用户一换问法就可能崩
4. 本质仍然是工作流节点，而不是通用能力

### 7.2 正确方向：原子工具 / 原子 skills

工具应该尽量少、尽量硬、尽量通用。

也就是说：

- 工具负责“能力”
- 模型负责“组合能力”

这样工具才写得完，意图也才有泛化能力。

## 8. 建议的空间 Skills 分层

当前推荐做成 `3 + 1` 层原子 skill。

### 8.1 `postgis_skill`

这是精确空间事实层。

#### 它负责什么

1. 精确几何关系
2. 距离计算
3. 范围过滤
4. 聚合统计
5. 拓扑关系判断
6. 输出结构化查询结果

#### 建议暴露的接口

1. `get_schema()`
2. `get_table_catalog()`
3. `validate_spatial_sql(sql)`
4. `execute_postgis_sql(sql, params)`
5. `geometry_buffer(geometry, meters)`
6. `geometry_intersects(a, b)`
7. `geometry_within(a, b)`
8. `geometry_centroid(geometry)`

#### 注意

这个 skill 不应该是“危险裸 SQL 执行器”，而应该是：

- 强白名单
- 只读
- 带 `LIMIT`
- 带超时
- 带 SQL AST / 规则校验

### 8.2 `spatial_encoder_skill`

这是空间语义能力层。

#### 它负责什么

1. 空间语义编码
2. 模糊空间意图映射
3. 区域相似性判断
4. 语义候选打分

#### 建议暴露的接口

1. `encode_spatial_text(text, scope?)`
2. `encode_region(region_spec)`
3. `score_spatial_match(query_embedding, candidate_embeddings)`
4. `predict_region_affinity(query, candidate_regions)`

#### 注意

这个 skill 不负责精确事实，它负责“语义近似”。

### 8.3 `spatial_vector_skill`

这是向量召回层。

#### 它负责什么

1. 向量候选召回
2. 相似区域召回
3. 模糊语义候选 narrowing
4. 为 PostGIS 精查提供候选集

#### 建议暴露的接口

1. `search_spatial_vectors(query_embedding, top_k, filters?)`
2. `search_similar_regions(region_embedding, top_k)`
3. `search_semantic_pois(text_or_embedding, bbox?, top_k?)`

#### 注意

它更像 retrieval，不应该伪装成最终分析器。

### 8.4 `route_distance_skill`

这是现实可达性层。

#### 它负责什么

1. 路网距离
2. 步行 / 驾车 / 骑行时间
3. 现实可达性判断

#### 建议暴露的接口

1. `get_route_distance(point_a, point_b, mode)`
2. `get_travel_time(point_a, point_b, mode)`

#### 为什么必须单列

因为：

- 直线距离 != 步行距离
- 球面距离 != 实际到达成本

这件事在“最近地铁站”“适合开店”“服务覆盖半径”等问题里非常重要。

## 9. 为什么这些 skills 更像“给大模型的置信来源”

这部分是当前方向非常核心的一点。

模型未来的“可信”，不应该来自“它觉得自己懂空间”，而应该来自：

1. PostGIS 给几何真相
2. 空间编码器给空间语义
3. 向量检索给候选召回
4. 路网工具给真实可达性

也就是说：

> 模型负责思考与编排，skills 负责给证据。

这样做的好处：

1. 证据来源可审计
2. 错误更容易定位
3. 能力边界清楚
4. 未来可替换单个 skill，而不必推翻整个系统

## 10. 当前最值得验证的主线方案

这是接下来最建议投入精力去验证的方案。

### 10.1 主线方案

#### 大脑层

使用强模型作为主控制脑：

- 能读系统 prompt
- 能理解用户自然语言空间问题
- 能看 tool schema / skill contract
- 能决定调用哪几个原子 skills
- 能读回结果并继续推理

#### 工具层

使用原子化空间 skills：

- `postgis_skill`
- `spatial_encoder_skill`
- `spatial_vector_skill`
- `route_distance_skill`

#### 执行层

本地后端负责：

1. 接住模型的 function call
2. 做参数校验
3. 执行 skill
4. 返回结构化结果

#### 表达层

最终回答分两种：

1. 结构化视图
2. 自然语言总结

但自然语言必须建立在真实证据返回之后。

### 10.2 当前推荐的推理方式

建议流程：

1. 模型先看问题
2. 如果需要精确事实，优先调 `postgis_skill`
3. 如果需要模糊空间语义，调 `spatial_encoder_skill + spatial_vector_skill`
4. 如果涉及可达性，调 `route_distance_skill`
5. 如果结果还不够，再继续 function calling
6. 最终输出答案

### 10.3 为什么这条线优于“先训 1.7B 小模型”

因为这条线先验证的是：

- 架构是否对
- 工具是否够原子
- 模型是否真能现场组合工具

一旦这条线成立，小模型蒸馏才有意义。  
否则只是在错误架构上做成本优化。

## 12. 当前最重要的技术研究问题

当前值得重点研究的，不是“怎么继续调 planner prompt”，而是下面这些问题：

### 12.1 Text-to-Spatial-SQL

研究点：

1. 如何让大模型根据 schema 生成正确的 PostGIS SQL
2. 如何控制 SQL 安全
3. 如何做 SQL 错误恢复与再尝试
4. 如何让模型知道什么时候该用 SQL，什么时候该用向量检索

### 12.2 Tool Selection / Function Calling

研究点：

1. 如何设计 skill contract，让模型更容易调用
2. 如何避免工具歧义
3. 如何减少无效调用
4. 如何做多轮工具调用后的状态收敛

### 12.3 结果压缩与证据表达

研究点：

1. 原始结果如何压成 Evidence View
2. 什么结果应该表格化
3. 什么结果应该视图化
4. 什么结果应该有不确定性提示

### 12.4 Skill 可靠性与安全性

研究点：

1. 只读 SQL 安全壳
2. 执行超时与重试
3. schema 白名单
4. 工具错误回传格式
5. 审计日志

## 13. 测试方案

这部分必须写清楚，因为未来另一个窗口 AI 接手时，不能只知道“方向”，还得知道怎么验证方向是不是跑偏了。

### 13.1 测试目标

当前测试不是只测“答得像不像”，而是测：

1. 是否调用了正确的技能
2. 是否能拿回真实空间证据
3. 是否减少了预制工作流依赖
4. 是否提高了泛化能力

### 13.2 测试分层

#### A. Skill 单测

每个 skill 都要有自己的单测：

1. `postgis_skill`
   - schema 获取
   - SQL 校验
   - 只读执行
   - geometry helper

2. `spatial_encoder_skill`
   - 编码成功
   - 相似性评分输出稳定

3. `spatial_vector_skill`
   - top-k 召回
   - filter 生效

4. `route_distance_skill`
   - 输入点合法
   - 输出距离与时间字段完整

#### B. Function Calling 集成测试

测试重点：

1. 大模型能否正确选择 skill
2. 大模型能否正确绑定参数
3. 技能执行失败时能否自修复一次
4. 结果回传后能否继续推理

#### C. End-to-End 回归测试

使用真实问题测试整条链路。

### 13.3 最低回归问题集

建议至少覆盖下面这些问题：

#### 精确查询类

1. `湖北大学最近的地铁站，站口也列出来`
2. `湖北大学附近 1km 内有哪些公交车站`
3. `武汉大学附近有哪些医院`

#### 模糊语义类

4. `湖北大学附近配套怎么样`
5. `武汉大学附近适合开什么店`
6. `和武汉大学周边气质相似的片区有哪些`

#### 比较类

7. `比较武汉大学和湖北大学附近的业态差异`
8. `武大和湖大谁周边餐饮更活跃`

#### 复杂复合类

9. `湖北大学附近适合开咖啡店吗，考虑地铁可达性和学生消费场景`
10. `给我找几个离湖北大学近、但不在校门口最拥挤路段的咖啡店候选`

#### 非空间 / 边界类

11. `帮我解释一下微积分基本定理`
12. `这个圈里的配套如何`（有 geometry）

### 13.4 关键验收指标

不要只看最终答案，要看这些指标：

1. `tool_selection_accuracy`
   - 技能选对了吗

2. `argument_binding_accuracy`
   - 参数绑对了吗

3. `sql_valid_rate`
   - Spatial SQL 生成是否合法、可执行

4. `evidence_grounded_answer_rate`
   - 最终答案是否有明确证据来源

5. `avg_tool_calls_per_query`
   - 平均调了几个工具

6. `fallback_rate`
   - 失败回退比例

7. `p50 / p95 total latency`
   - 时延表现

8. `generalization_on_unseen_queries`
   - 未见过问法的泛化表现

### 13.5 当前阶段的性能预期

这一阶段先看趋势，不先承诺绝对值。

目标趋势：

1. 简单精确查询：
   - 大幅短于 V3 双 LLM 链路

2. 复杂复合查询：
   - 允许比简单题慢，但必须比“重工具预制工作流”更泛化

3. 工具调用数：
   - 越少越好，但不能牺牲正确性

## 18. 最后一段总结

当前项目真正要解决的，不是“再多补几个空间意图”，也不是“再多写几个分析工具”。

真正要解决的是：

> 怎么让大模型在理解用户自然语言空间意图的基础上，学会调用空间工具、调用空间编码器、调用 PostGIS 和向量检索，去做一个真正的空间 Agent。

当前最优先的验证路线是：

**强模型大脑 + 原子化空间 skills + Function Calling + 真实空间证据回传**

小模型微调不是被彻底否定，而是应该后移到：

**强模型主线验证成立之后，再作为降本与本地化补充方案。**

如果后续出现方向争议，请优先回到这份文档的三条判断标准：

1. 这个方案是不是更接近 Agent，而不是更接近固定工作流？
2. 这个方案是不是让工具更原子，而不是更重？
3. 这个方案是不是让模型更像“大脑”，而不是更像“planner 文书机”？

只要这三条答案是“是”，大概率就在正确方向上。
