# 空间规划器前台渐进式实施计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**目标：** 将 V3 从"靠规则兜答案的空间问答后端"逐步改造成"LLM 负责查询规划、双模型空间编码器 + PostGIS 负责提供空间事实、后端只负责协调执行"的 Geo RAG 服务前台。

**核心思想（不容商量的底线）：**

本系统是一个 **Geo RAG**——底层空间能力来自两个引擎的协作：

1. **PostGIS（精确空间计算层）**：距离计算、半径过滤、几何查询——这些是精确的、可靠的，不依赖 ML。
2. **双模型空间编码器（语义空间层）**：
   - **POI 级编码器**（352 维）：区域分类（F1 90.48%）、语义近邻检索（IntraRecall 91.42%）、方向判断（99.98%）。它学到的是**语义聚类**，不是地理距离排序（Pearson 0.37，远低于 0.90 目标）。
   - **Cell 级编码器**：宏观区域相似度分析、业态结构对比。

用户的空间问题，问谷歌、问百度、问高德、问普通 LLM，要么没有答案，要么瞎编。我们不一样，因为我们把 PostGIS 的精确空间能力 + 双模型编码器的语义空间能力挂载到了 LLM 上。

**⚠️ 能力边界（后续实施者必须牢记）：**

| 能做 | 不能做 |
|------|--------|
| PostGIS 半径过滤 → 精确的"这附近有什么" | 编码器距离保真 → 不能用 embedding 做精确距离查询 |
| 编码器语义排序 → "哪些 POI 和这个区域最像" | 编码器范围查询 → Range IoU 仅 27%，不靠谱 |
| 编码器区域分类 → "这个地方属于什么类型区域" | 编码器理解自然语言 → 编码器只吃坐标，不吃文本 |
| Cell 编码器 → "哪些区域和这个区域业态结构相似" | - |

**tool schema 的设计原则：`search_nearby_pois` 等检索工具的参数应围绕 PostGIS 的能力设计（anchor + radius + filter），embedding 的角色是排序和增强，不是检索本身。**

**后端的唯一职责是"服务前台"**：本身什么都不知道，但知道怎么去查"PostGIS 精确空间能力 + 编码器语义能力 + LLM 语言能力"。仅此而已。写死规则是死路——用户的问法无穷无尽，难不成要收集每一种话术偏好？规则写不完的。

正确分工是：

1. 用户提问
2. LLM 把问题翻译成查询计划
3. 后端执行查询计划，去问空间编码器 / 检索层
4. 后端把证据回填给 LLM
5. LLM 基于证据生成最终回答

**技术栈：** Node.js(Fastify/Vitest) + Python 空间编码器服务 + Ollama/LM Studio + PostGIS/pgvector + SSE

## 一、为什么要换方向

当前旧线路能解决一部分表面问题，但越往后越容易陷入三个死局：

1. 用户问题形态无限多，规则永远补不完。
2. support-gap / overview / comparison 这类题本质不是"分类题"，而是"空间查询规划题"。
3. 规则越多，越容易把后端变成一个自以为懂空间、实际不断补丁的假专家。

你真正要的不是：
- "写一千套规则，把用户可能的话术都兜住"

而是：
- "后端知道怎么去调动真正懂空间的编码器和真正擅长语言组织的 LLM"

所以后续设计必须遵守一个底线：

**能交给规划器解决的问题，就不要继续往规则里堆。**

## 二、目标状态

未来对一个问题，例如：
`比较武汉大学和湖北大学附近的业态差异。`

理想流程应该是：

1. LLM 判断这是一个"双锚点比较型空间问题"。
2. LLM 输出结构化计划，例如：
   - 先解析两个锚点
   - 对每个锚点取同口径空间证据
   - 判断哪些特征属于"共性背景"，哪些属于"真正差异"
   - 如果证据不够，再追加一轮查询
3. 后端逐步执行这些查询。
4. PostGIS 精确过滤 → 编码器语义排序增强 → 返回方向、区域分类、邻近 POI、宏观 cell 等证据。
5. LLM 基于证据做比较，并生成用户能听懂的话。

这里最重要的一点是：

**后端自己不装懂，只负责把"问谁、怎么问、拿回什么、下一步问什么"这件事组织起来。**

## 三、架构边界重定义

### 1. `rules_line`

这是旧线路，已经被明确视为 deprecated。

职责：
- 保留现网兼容能力
- 作为回归基线
- 在新线路没准备好前兜底

不再承担的职责：
- 继续无限扩写规则
- 继续作为主线方向演进

### 2. `planner_line`

这是未来主线。

职责：
- 让 LLM 负责查询规划
- 让后端负责计划执行
- 让空间编码器负责提供空间事实

### 3. `spatial_core`

这是稳定能力层，不应依附于某条线路。底层由两个引擎协作提供空间能力：

**引擎 A：PostGIS（精确空间计算层）**
- POI 半径过滤（ST_DWithin）、距离计算（Haversine）
- 地名模糊匹配（quickSearchPois）
- 几何构建（边界、凸包、缓冲区）
- 这是检索的骨架——所有"附近 N 米内"的查询都由 PostGIS 做精确过滤

**引擎 B：双模型空间编码器（语义空间层）**
- POI 级编码器（352 维向量）：区域分类、语义排序、方向判断
- Cell 级编码器：宏观区域相似度、业态结构对比
- 这是检索的增强层——PostGIS 过滤后的候选集由编码器做语义排序和空间 enrichment

`spatial_core` 应包含：
- PostGIS 查询封装（半径过滤、地名解析）
- POI 级编码器客户端（坐标 → embedding → 语义排序/区域分类）
- Cell 级编码器客户端（宏观区域分析）
- 两者协同的混合检索编排（PostGIS 过滤 + 编码器排序）
- 空间几何构建（边界、热点）
- POI enrichment（方向、距离、区域标注）
- 证据规范化

原则：
- `rules_line` 和未来的 `planner_line` 都可以调用它
- 它本身不应该带强烈的任务写死逻辑
- 工具的输入参数应围绕 PostGIS 能力设计，编码器在内部做排序增强而非暴露给 planner

## 四、工程实施总原则

### 原则 1：先求准，再求快

这一轮不追求先把速度做到极致。
先保证规划出来的查询是对的，空间证据是可信的，回答不瞎编。

### 原则 2：阶段推进，不一口吃完

每一阶段只解决一个主要问题，不同时追三四个目标。

### 原则 3：每阶段都用固定 10 题回归

每做完一个可独立评估的阶段，都要重新跑这 10 个问题：

1. `武汉大学附近有哪些咖啡店？`
2. `湖北大学附近有哪些地铁站？`
3. `武汉大学附近有哪些医院？`
4. `武汉大学附近有哪些商超？`
5. `光谷附近有哪些咖啡店？`
6. `请分析武汉大学附近的配套、热门业态和明显缺口。`
7. `请分析湖北大学附近的配套、热门业态和明显缺口。`
8. `请概览武汉大学附近的空间结构和业态分布。`
9. `武汉大学附近适合布局什么业态？`
10. `比较武汉大学和湖北大学附近的业态差异。`

### 原则 4：决定下一步要看对比，不看感觉

每次阶段结束后都要回答：

1. 哪几题明显变好了？
2. 哪几题没动？
3. 哪几题暴露了新的问题？
4. 下一阶段应该继续收哪一个瓶颈？

### 阶段 B：定义 planner_line 的契约

**目标：**
先把"LLM 应该怎么规划"和"后端应该怎么执行"写成稳定契约，不急着做复杂行为。

> **⚠️ 范围控制**：阶段 B 包含两类性质不同的任务——"定义契约"（设计型）和"分析遗留依赖"（考古型）。为避免在依赖梳理中陷入泥潭而迟迟产不出 schema，将阶段 B 拆分为三个可独立验收的子阶段：
>
> - **B1**：schema + validator（纯契约定义，1-2 session）
> - **B2**：prompts + tool catalog（LLM 对接层，1-2 session）
> - **B3**：依赖审计 + 衔接分析（分析型，1 session）
>
> 执行顺序：B1 → B2 → B3。

**要产出的核心内容：**

#### B1. 规划输出 schema（子阶段 B1）

建议先约束成 JSON，对外不追求完美，先追求稳定。

**核心设计原则：**

1. **`steps` 是唯一的执行描述** — LLM 规划的核心产出是 steps 序列，不需要同时生成宏观策略和微观步骤两层描述
2. **`task_type` 是可选 hint** — 真正的规划器通过构造 steps 来表达意图，而非做"分类题"。task_type 可由后端从 steps 自动推断（如 steps 中有 2 个 `resolve_anchor` → 推断为 `dual_anchor` 模式）
3. **预留条件分支** — 阶段 D 多轮规划迟早需要条件逻辑，schema 中先预留 `condition` 字段

最低版本建议字段：

```json
{
  "task_type_hint": "nearby_lookup",
  "user_goal": "一句人话描述用户真实想知道什么",
  "anchors": [
    {
      "name": "武汉大学",
      "role": "primary"
    }
  ],
  "steps": [
    {
      "step_id": "s1_resolve",
      "tool": "spatial_core.resolve_anchor",
      "input": { "place_name": "武汉大学" },
      "expect_output": ["anchor"],
      "condition": null
    },
    {
      "step_id": "s2_search",
      "tool": "spatial_core.search_nearby_pois",
      "input": {
        "anchor": "$ref:s1_resolve.anchor",
        "radius_m": 1200,
        "category_filter": "餐饮美食",
        "limit": 30
      },
      "expect_output": ["pois", "total_count"],
      "condition": null
    },
    {
      "step_id": "s3_expand",
      "tool": "spatial_core.search_nearby_pois",
      "input": {
        "anchor": "$ref:s1_resolve.anchor",
        "radius_m": 2000,
        "category_filter": "餐饮美食",
        "limit": 30
      },
      "expect_output": ["pois", "total_count"],
      "condition": "$ref:s2_search.total_count < 5"
    }
  ],
  "stop_conditions": {
    "max_rounds": 1,
    "max_queries": 4,
    "min_evidence_items": 5
  },
  "answer_frame": {
    "style": "comparison | gap | overview | lookup",
    "must_ground_in_evidence": true,
    "required_sections": [],
    "forbidden_claims": ["不能凭猜测声称某处缺少某类业态"]
  }
}
```

**关于 schema 的关键设计决策：**

1. **去掉了 `search_strategy`**：原版中 `search_strategy.mode`（single_anchor / dual_anchor）与 `steps` 中的具体查询步骤语义重叠。当 `search_strategy.need_macro = false` 但 `steps` 里包含 `macro_cell_analysis` 时就会冲突。后端应从 steps 自动推断宏观策略。
2. **`task_type` → `task_type_hint`**：降级为可选 hint。LLM 可以填也可以不填，后端可从 steps 的组合反推 task_type。验收标准改为"steps 执行后能否获取足够证据"，而非"task_type 分类是否正确"。
3. **预留 `condition` 字段**：阶段 B1 不实现条件逻辑（`condition: null` 即可），但 schema 先预留字段。避免阶段 D 多轮规划时被迫修改 schema 引发全链路回归。
4. **每个 step 必须有 `input` 和 `expect_output`**：这是让 planValidator 能静态检查 plan 合法性的基础。
5. **支持 `$ref:step_id.field` 与并行语义**：在步骤间传递数据。**系统将按拓扑排序执行 steps**，没有 `$ref` 依赖关系的步骤必须支持并行执行（如双锚点对比时的两次 `resolve_anchor`）。`$ref` 只能引用已完成步骤的输出。
6. **明确 `min_evidence_items` 的临时占位**：在阶段 B1 的 `planValidator.js` 中需明确指出该字段暂用作声明，阶段 D 实现多轮规划时再精确定义其指代物（POI 数量或证据块数量）。
7. **`tool` 字段的合法值由 `spatial_core.toolCatalog` 统一定义**（见 B2）。

#### B2. 执行层 schema 与 spatial_core tool catalog（子阶段 B2）

后端本身什么都不知道，只知道怎么查。`spatial_core` 是 PostGIS + 双模型编码器能力的统一接入层——LLM 生成的 plan 里每个 step 都必须调用这里的 tool，绝不直接操作底层。

**V3 当前可调用的空间能力（tool catalog 最低集合）：**

| Tool 名称 | 职责 | 底层实现 | 可靠度 |
|-----------|------|---------|--------|
| `spatial_core.resolve_anchor` | 将地名解析为经纬度坐标 + 基础意图提取 | PostGIS 模糊匹配 + intentService 规则/LLM | ⚠️ 高复杂度：含意图推断逻辑 |
| `spatial_core.search_nearby_pois` | 近邻 POI 检索 | PostGIS 半径过滤 + 编码器语义排序 | ✅ 可靠：PostGIS 做精确过滤，编码器做排序增强 |
| `spatial_core.vector_search` | 语义向量检索（编码器排序） | POI 编码器 352 维向量 + 余弦相似 | ✅ 语义排序强（IntraRecall 91%），但不能做精确距离查询 |
| `spatial_core.macro_cell_analysis` | 宏观 cell 业态分析 | Cell 级编码器 + PostGIS | ✅ 已有独立模块 |
| `spatial_core.spatial_encode` | 查询点的空间 enrichment（方向/区域分类） | 方向=三角函数(精确)，区域=POI 编码器(F1 90%) | ✅ 方向精确，区域分类可靠 |
| `spatial_core.build_boundary` | 空间边界与热点构建 | PostGIS 几何 + 编码器 enrichment | ⚠️ 有耦合：依赖 retrieval 层多个模块 |
| `spatial_core.infer_intent_legacy` | 旧规则引擎意图推断（过渡期兜底） | intentService.js | 🔄 过渡用：阶段 E 迁移完成后废弃 |

> **⚠️ 给 schema 设计者的硬约束**：`search_nearby_pois` 的 input 必须包含 `anchor` + `radius_m`（PostGIS 参数），可选 `category_filter`/`target_region`（过滤参数）。不能让 LLM 以为可以用 embedding 做精确距离或范围查询——编码器的 Pearson 只有 0.37，Range IoU 只有 27%。

**关于 tool catalog 的关键修正（相对原版）：**

1. **移除了 `support_bucket_stats`**：审查 `chatPipeline.js` 后发现，support_buckets 数据来源是 `macroCellSummary.support_buckets`（宏观 cell 搜索结果），如果宏观搜索没命中才 fallback 到 `summarizeSupportBuckets(filteredResults)`（从 POI 结果推算）。它**不是一个独立的查询工具，而是对其他工具结果的二次加工**——应在 evidenceBundle 的构建逻辑中处理，不暴露给 LLM 规划器。LLM 只需要规划"查什么"，不需要规划"怎么统计"。

2. **增加了 `infer_intent_legacy`（过渡期兜底 tool）**：`intentService.js` 有 1484 行，其中约 60% 是意图理解逻辑（task_type 推断、analysis_facets 推断、anchor_mode 推断），这些在阶段 C 实现前不能丢弃。增加此 tool 让 planner 可以选择"自己推断"或"调 legacy 兜底"，在阶段 E 完成迁移前不会断档。

3. **校正了 `resolve_anchor` 的复杂度评估**：原计划将其描述为"简单地名解析"，但实际上 `intentService.js` 中 `parseIntent()` → `parseIntentWithSmallLLM()` → `stabilizeIntentResult()` 是一条完整的 LLM 调用 + 规则兜底 + 交叉稳定化链路。`resolve_anchor` 初期只需提取"地名→坐标"部分，但必须在 tool schema 文档中显式记录"意图推断职责暂由 `infer_intent_legacy` 承接"。

每个 tool 必须在 `toolSchemas.js` 中定义完整的 input/output JSON schema。LLM 拿到 tool catalog 才知道"我能问什么、怎么问、会拿回什么"——这是让 LLM 真正成为规划器而非模板润色器的关键。

**最低版本执行层需要支持：**

1. 锚点解析（`resolve_anchor`）
2. nearby POI 检索（`search_nearby_pois`）
3. 宏观 cell 检索（`macro_cell_analysis`）
4. 双锚点并行比较
5. 证据收集与规范化

#### B3. 证据回填 schema（仍属子阶段 B1 产出）

LLM 最后吃的不是零散字段，而是统一 evidence bundle。后端把空间编码器查回来的事实打包成标准格式交还给 LLM，LLM 只负责用人话把这些事实讲清楚。

至少应包含：

1. anchors
2. nearby_pois
3. representative_pois
4. support_buckets
5. support_bucket_metrics
6. population_metrics
7. boundary / cluster / region summary
8. uncertainty
9. execution_trace

**每个证据块必须附带 provenance 元数据：**

```json
{
  "support_buckets": ["..."],
  "support_buckets_meta": {
    "source": "postgis_spatial_filter | poi_encoder_semantic_rank | cell_encoder_macro_analysis",
    "source_detail": "postgis 做半径过滤，poi_encoder 做语义排序增强",
    "confidence": 0.82,
    "sample_size": 47,
    "generated_by_step": "s3_macro",
    "data_freshness": "2026-03-15T00:00:00Z",
    "staleness_warning": false
  }
}
```

没有 provenance，LLM 无法判断证据质量，会把低置信度统计结果当确定性事实写进回答——这就回到了"瞎编"的老路。

> **补充：`data_freshness` 与 `staleness_warning`**：POI 数据有时效性，如果数据采集日期很久远，LLM 应在回答中标注"数据截至 XXXX 年"。在 provenance 中加入时间戳和过期警告字段，让 LLM 有能力判断是否需要声明数据时效。

### 阶段 C：单轮 planner_line 原型

**目标：**
先做最小可用版：
一次规划 -> 一次执行 -> 一次回答

**为什么先做单轮：**
因为多轮规划虽然更强，但复杂度更高。
先验证"LLM 规划是否真的比规则路线更准"，再加多轮。

**要做的事：**

#### C1. 新建 plannerService

职责：
- 接收用户 query
- 调 LLM 生成结构化 plan（基于 B2 的 plannerPrompts）
- 通过 planValidator 校验 schema
- 若校验失败，可选调 `infer_intent_legacy` 作为兜底
- 输出 validated plan

#### C2. 新建 planExecutor

职责：
- 接收 validated plan
- 通过 `toolRunner` 逐步执行 steps（按 step_id 拓扑排序）
- 处理 `$ref` 引用解析
- 跳过 `condition` 不满足的 step（为阶段 D 预留）
- 收集 evidence bundle

#### C3. 新建 answer synthesis

职责：
- 把 evidence bundle 交给 LLM
- 限制必须基于 evidence 作答
- 先不用太多风格化模板

#### C4. 路由与共存策略

职责：
- 阶段 C/D 期间，系统需要处理新老架构共存。
- 建议在 `chatPipeline.js` 的最外层加一个基于 `task_type`（或者特例白名单）的路由控制。
- 只有被支持的白名单任务（如 `nearby_lookup`, `area_overview`）进入 `plannerService` 执行，其他兜底走现有的 `rules_line` 主流程。

**建议文件：**
- Create: `V3-GeoEncoder-RAG/services/planner_line/plannerService.js`
- Create: `V3-GeoEncoder-RAG/services/planner_line/planExecutor.js`
- Create: `V3-GeoEncoder-RAG/services/planner_line/evidenceBundle.js`
- Create: `V3-GeoEncoder-RAG/services/planner_line/answerSynthesis.js`
- Create: `V3-GeoEncoder-RAG/services/__tests__/planner_line/*.spec.js`

**第一阶段建议只接入的任务：**

1. `nearby_lookup`
2. `area_overview`

原因：
这两类任务复杂度更低，更适合先验证 planner 是否比规则更稳。

**验收标准：**

1. planner_line 可独立跑通
2. 至少在 Q1-Q5、Q8 上能形成稳定 evidence-grounded answer
3. 能和 rules_line 并排对比

**目标：**

**适用问题：**

## 七、回归与决策机制

每完成一个阶段，统一做下面 4 步：

1. 运行相关单测
2. 运行固定 10 题
3. 记录前后对比
4. 决定下一阶段只解决一个最主要问题

禁止：

1. 没有阶段回归就继续往前冲
2. 一次阶段同时追多个目标
3. 看到局部问题就又回到补规则

## 九、这一版计划的判断标准

1. 规则代码越来越少，只保留必要兜底
2. planner 输出越来越稳定
3. PostGIS + 编码器返回的空间证据越来越成为主角
4. LLM 越来越像查询规划器，而不是模板润色器
