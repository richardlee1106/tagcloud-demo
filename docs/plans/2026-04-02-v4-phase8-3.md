## 3. 关键结果

### 3.1 监控口径真正落地了

之前的 V4 health 只能看到：

1. provider 是否 ready
2. memory / dependency 是否 degraded

现在还能看到：

1. 请求数量
2. 滚动窗口 `p50 / p95 latency`
3. `sql_valid_rate`
4. `evidence_grounded_answer_rate`

这意味着后面接 Redis 或远程依赖时，不再是“只能靠感觉判断系统是不是变差了”。

### 3.2 10 题回归不再散在测试里

本轮把已有关键题型收敛成固定 fixture，覆盖：

1. 附近 POI
2. 最近地铁站
3. 最近地铁站 recovery
4. 相似片区
5. 双地点餐饮比较
6. 锚点未解析澄清
7. provider unavailable fallback
8. polished answer provider
9. 双地点地铁分布比较
10. provider throwing 时的 graceful degradation

### 3.3 MiniMax 的角色被正式写进工程

本轮不是只在文档里说“以后用 MiniMax”，而是把它正式变成：

> **Phase 8.3 真编排 smoke 的主入口。**

当前 smoke 策略是：

1. 如果 MiniMax 环境变量未配置，自动 skip
2. 如果环境已配置，直接跑真实编排 smoke
3. 真服务 smoke 现已固定为 10 题 corpus，每题独立用例 + 单题超时控制，避免多轮 function-calling 被共享超时误伤

### 3.4 Redis 与三类远程依赖先把“验真脚手架”补齐

这轮没有伪造“已经跑过真实生产环境”，而是做了两件更诚实的事情：

1. 保留现有 `remote-first + fallback` 主逻辑
2. 把 Redis / FAISS / 路网 / Python 编码器的真环境 smoke 写成可直接执行的测试入口

### 3.5 根目录配置终于能被 V4 真正吃到了

之前一个很实际的问题是：

1. 根目录已经有 `.env / .env.v4`
2. 但 `V4-GeoLoom-beta` 默认只会尝试读自己目录下的 `.env`
3. 结果 smoke 和后端很容易出现“明明项目里有配置，但 V4 看不见”

本轮补了 `loadRuntimeEnv()` 之后：

1. `server.ts`
2. 回归 harness
3. MiniMax smoke
4. 远程依赖 smoke

都会自动按顺序读取：

1. 仓库根目录 `.env`
2. 仓库根目录 `.env.v4`
3. `V4-GeoLoom-beta/.env`

这样后面只要把真实环境配置放在项目现有位置，V4 就能直接吃到，不用再额外复制配置文件。

也就是说：

- 代码已经准备好“上真环境就能测”
- 但这轮本机环境没有对应配置时，会自动 skip，不会假装已验收
