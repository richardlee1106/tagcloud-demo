# V2 GIS Agent 架构复盘与后续优化建议（2026-03-09）

## 1. 这份文档是干什么的

这份文档只回答三个问题：

1. `V2` 现在到底做到了哪一步
2. 现在的实现有没有偏离原来的设计路线
3. 如果继续做成一个更完整、更高阶的 GIS Agent WebGIS 系统，下一步最值得投入的点是什么

---

## 2. 当前完成情况概览

### 2.1 已完成的核心能力

- `V2-Agent-backend` 已独立于 `V1` 存在，可单独启动和验证
- 已有 `Intent Router v2`
- 已有模板重排逻辑
- 已有 `DSL` 校验
- 已有 `L1/L2` 缓存
- 已有 `Deep Lane` 状态机、`deep.patch`、`deep.final`
- 已有 `async_deep` 异步补全
- 已有 `Redis + PostgreSQL + file fallback` 的作业状态持久化
- 已有 `Python tool plane` 最小骨架
- `Node -> Python` 代理执行已打通
- 已有 `V1/V2` 前端切换入口
- 已有 `V1/V2` 同请求真实对比脚本
- 已有 `live benchmark / compare / summary report` 产物能力

### 2.2 当前最能说明问题的真实结果

- `V2` 可以稳定完成：
  - `fast.result -> deep.accepted -> deep.patch -> deep.final`
- 真实同请求对比里：
  - `V1` 首响更快
  - `V2` 总完成时间显著更快
- 真实持久层检查里：
  - `Redis` 延迟低，适合热状态
  - `PostgreSQL` 适合耐久存储

## 4. 当前实现相对原设计的偏离点

### 4.1 偏离点一：当前更像“高质量工程原型”，还不是最终形态

虽然主链路已经通了，但离原始大规格设计还有差距：

- 还没有真正完整的多能力域工具生态
- 还没有真正的复杂规划层
- 还没有完整的回放、混沌、压测体系
- 还没有成熟的 dashboard / alert / SLA 看板

说白话：
- 现在的 `V2` 已经是“能打的最小系统”
- 但还不是“企业级最终形态”

### 4.2 偏离点二：Node 仍然偏重

原本长期方向里，空间重计算更适合进一步从 `Node` 侧剥离。

现在虽然已经引入 `Python tool plane`，但：

- `Intent / Plan / State / Metrics / Persistence orchestration` 还都在 `Node`
- `Node` 还承担了大量系统编排逻辑

这不是错误，但意味着：
- 当前仍然是“Node 为主、Python 为工具层”的架构
- 还不是完全意义上的“控制平面 / 执行平面”彻底解耦

### 4.3 偏离点三：V1/V2 比较环境仍不够稳

现在已经能做真实对比，但依赖启动状态仍然不够稳定：

- `V1` 很依赖 `PostgreSQL` 和旧链路
- 一旦依赖抖动，`compare:live` 就会降级

这说明：
- 系统主能力没问题
- 但“联调和回归比较环境”的工程稳定性还不够强

---

## 5. 当前架构里最值得警惕的问题

### 5.1 问题一：首响和总完成表现分裂

现在的真实结果很清楚：

- `V1` 首响更快
- `V2` 总完成更快

这说明 `V2` 的关键问题已经不是“算得慢”，而是：
- 首个对用户可见的结果还不够早

这会影响用户主观体验。

### 5.2 问题二：工具能力还是偏少

当前主要还是围绕：

- `clip`
- `buffer`
- `merge`
- `export_geojson`

这足够证明架构成立，但不足以支撑更复杂 GIS Agent。

如果不继续扩能力域，系统会长期停留在：
- 架构先进
- 但业务能力偏薄

### 5.3 问题三：观测有了，但还不够“长期化”

现在已经有：

- metrics
- live benchmark
- compare
- summary report

但这些还偏“脚本驱动”。

下一步如果不做：

- 固定目录归档
- 时间序列化
- dashboard
- alert

那就还不算真正完成“持续运维化”。

### 5.4 问题四：V1 仍然在影响 V2 的评估效率

只要还需要频繁和 `V1` 对比，就必须维护一套较脆弱的旧环境。

这带来的问题是：

- 工程成本变高
- 对比脚本复杂
- 问题定位会被旧系统拖慢

长期看，必须明确：

- 到什么标准可以减少对 `V1` 的强依赖
- 到什么标准可以只保留少量回归样本，而不再全量联调

## 6. 下一阶段最值得做的优化方向

下面按优先级排序。

### P0：首响优化

目标：
- 让 `V2` 不只是总完成快，还要“更早给用户一个像样的东西”

建议：

- 把 `fast.result` 再拆得更轻
- 先返回：
  - 最小摘要
  - 主意图
  - 是否进入 deep lane
- 把较重的 artifact 细节和补充说明后移

为什么这件事优先级最高：
- 因为它最直接影响主观体验
- 也是当前 V1 相对 V2 唯一明显更优的地方

### P1：扩第二、第三能力域工具

建议至少扩到：

- `overlay/intersection`
- `spatial join`
- `distance matrix / nearest`
- `raster sample`

原因：
- 现在架构已经证明可行
- 下一步不能只继续围绕 `buffer/merge`
- 否则系统会像“架构漂亮但工具箱太小”

### P1：把指标从“脚本输出”推进到“长期看板”

建议：

- 把 `metrics` 和 `live reports` 固定落盘
- 建一个轻量 dashboard 目录
- 至少保留：
  - 每日 benchmark
  - 每日 compare
  - persistence health 快照

### P2：明确 V1 退出条件

建议定义一张表：

- 当 `V2` 在哪些指标上持续多少天超过 `V1`
- 就可以把 `V1` 从默认比较对象降级为“抽样回归对象”

这会极大减轻后续维护成本。

### P2：进一步语言边界优化

是否要继续保留 `Node orchestrator + Python tools`：

- 短期：是，没问题，工程效率很高
- 中期：建议把“重计算更集中的能力域”逐步继续下沉

不是现在立刻换语言，而是：
- 明确哪些算子值得下沉
- 哪些仍留在 Node 最合适

### P3：引入更正式的规划层

当前 `V2` 已有 DSL 和执行链，但“真正复杂任务规划”还偏弱。

长期若要做更高阶 GIS Agent，应该补：

- 多步计划
- 约束求解
- 工具选择评分
- 回退计划

这一步应该放在工具能力扩起来之后做。

## 7. 对编程语言与框架的判断

### 7.1 Node.js / Fastify

当前判断：
- 继续保留是合理的

原因：
- 控制平面、路由、SSE、编排都很合适
- 开发效率高
- 当前没有显示出必须替换的瓶颈

### 7.2 Python / FastAPI

当前判断：
- 继续强化，而不是削弱

原因：
- 空间算子、GeoJSON、未来 raster/vector 能力都更适合 Python 生态
- 当前作为 tool plane 很合适

### 7.3 是否需要 Go / Rust

当前判断：
- 现在不该引入

原因：
- 当前瓶颈不在“语言不够快”
- 当前最需要的是：
  - 首响优化
  - 工具扩展
  - 环境稳定
  - 指标闭环

在这些还没做完前，引入 Go/Rust 只会加大维护复杂度。

---

## 8. 建议的后续实施顺序

1. 先做 `V2 首响优化`
2. 再做 `第二、第三能力域工具`
3. 再做 `长期化 metrics / report / dashboard`
4. 再做 `V1 退出条件`
5. 最后再考虑更高级的规划层和更深的多语言拆分

---

## 9. 一句话结论

`V2` 现在已经不是概念验证，而是一个真正跑起来、能比较、能优化的系统雏形。

它当前最大的价值已经很明确：

- 总完成速度远优于 `V1`
- 可观测性和可调试性显著优于 `V1`
- 架构方向基本正确

它当前最大的短板也很明确：

- 首响还不够极致
- 工具能力域还太少
- 联调和长期运维化还没完全收口

所以接下来最值得做的，不是再重构一次架构，而是：

**把首响、工具域、长期指标这三件事做扎实。**
