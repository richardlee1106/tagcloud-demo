# V3 GeoEncoder RAG 空间智能规格说明

## 1. 概述

### 1.1 问题定义

传统 GIS + LLM 方案存在结构性缺陷：

- LLM 只能处理被文本化后的空间事实，例如“POI A 位于 POI B 东侧 500 米”。
- LLM 无法直接内化隐含的空间模式、拓扑关系、区域相似性以及多尺度地理结构。
- 当用户提出“找出与光谷核心区商业布局相似的区域”这类问题时，普通 LLM 只能给出泛泛而谈的解释，无法给出基于真实空间结构的推理结果。

### 1.2 产品目标

`V3-GeoEncoder-RAG` 的目标，不是让 LLM “更像地图一样说话”。

它的目标是让 LLM 能够：

- 计算空间
- 检索空间
- 比较空间
- 解释空间
- 把空间相似性当作一等语义信号来进行推理

核心机制是训练一个空间编码器，将点、线、面对象之间的空间关系编码成稠密向量，再通过检索和证据组装机制暴露给 LLM，使其能够进行基于空间向量的推理与回答。

### 1.3 用户价值

当空间编码器被成功挂载后，系统应从“会泛泛地谈武汉”升级为“能够基于武汉真实空间结构做判断”：

- 本地推荐：找到可达、可走、值得去的 POI
- 区域比较：识别与某个商圈、住宅区或混合功能区相似的区域
- 拓扑推理：基于道路结构、通达性和出行方式回答问题
- 时空解释：解释某个区域为何变化、如何变化、变化模式属于哪一类

## 2. 以结果为导向的成功定义

本项目的成功标准，不是单纯把离线模型指标做高，而是提升终端用户看到的空间推理质量。

### 2.1 必须达到的最终状态

挂载后的系统必须让 LLM 能够对如下类型的问题给出具体、可核验、有证据支撑的回答：

| 能力类别 | 示例问题 | 期望系统行为 |
|---|---|---|
| 本地空间检索 | “从武汉大学信息学部南门出发，步行 10 分钟内有哪些值得推荐的咖啡馆？” | 返回真实可达候选，并附带距离、时间、排序依据和路径相关解释 |
| 空间模式解释 | “光谷转盘附近为什么开了这么多密室逃脱？” | 用周边高校、商业存量、集聚效应、竞争密度等证据解释形成原因 |
| 拓扑与可达性比较 | “对南湖居民来说，街道口和光谷哪个更方便？” | 比较公共交通、自驾、骑行等维度，而不是只比较直线距离 |
| 区域相似性检索 | “找出与光谷核心区商业布局相似的区域。” | 基于多尺度空间语义返回 top-k 相似区域 |
| 时空演化分析 | “武昌区过去 5 年哪里的餐饮业态变化最大？” | 识别变化最明显的区域，概括变化模式，并解释背后驱动因素 |

### 2.2 不属于成功的情况

以下结果本身不能算项目成功：

- 只提升 Pearson 相关性
- 只提升 Silhouette 分数
- 只提升点级 embedding 的 KNN 重叠率
- 只能回答 POI 附近检索，不能回答区域级问题
- 只能处理点对象，忽略线和面对象

## 3. 空间智能能力分层

目标系统应被理解为一个分层能力体系。

| 等级 | 名称 | 描述 | 当前 / 目标 |
|---|---|---|---|
| L0 | 文本化空间描述 | 只能泛泛谈空间，没有真实本地空间智能 | 纯 LLM 基线 |
| L1 | 空间感知 | 能理解距离和相对接近关系 | 当前 V2.3 |
| L2 | 空间检索 | 能稳定找出真实邻近或相似对象 | V2.4 目标 |
| L3 | 空间理解 | 能理解方向、功能区和多尺度区域相似性 | V2.5 目标 |
| L4 | 空间推理 | 能解释空间模式、比较区域、结合拓扑和演化做推理 | V3 目标 |

### 3.1 版本映射

- `V2.3`：验证基础距离保持能力和局部 embedding 可行性
- `V2.4`：从空间感知升级为空间检索
- `V2.5`：增加方向语义和功能区语义
- `V3`：把多几何类型空间智能接入 RAG，并暴露给 LLM

## 4. 架构方向

### 4.1 核心决策

系统应从当前的“`POI 级 MLP 编码器`”，演进为“`网格级空间上下文编码器 + agent 投影层 + 检索推理层`”。

这是最关键的架构转向。

### 4.2 为什么必须转向

对于当前本机硬件条件以及最终要解决的“区域相似性推理”目标而言，直接把所有点、线、面对象作为一级训练对象，是错误的规模边界，也是错误的抽象边界。

正确的边界应是：

1. 先把原始几何压缩到空间网格单元
2. 在网格级学习带上下文的空间 embedding
3. 再把具体 agent 投影到这个空间语义空间中
4. 最后让 LLM 基于这些投影后的对象和区域进行检索与推理

### 4.3 推荐高层架构

```text
原始空间数据
  ├─ POI（点）
  ├─ 道路（线）
  ├─ AOI / landuse / block（面）
  └─ 可选时间快照
          ↓
离线空间预处理
  ├─ H3 网格映射 / polyfill / 线覆盖映射
  ├─ 多尺度邻域聚合
  ├─ 网格级特征张量构建
  └─ agent 到 cell 的映射表
          ↓
空间上下文编码器
  ├─ cell embedding 预训练
  ├─ 局部邻域语义学习
  ├─ 方向辅助任务头
  └─ 功能区语义任务头
          ↓
Agent 投影层
  ├─ 点 agent
  ├─ 线 agent
  ├─ 面 agent
  └─ 区域 / 聚类表示
          ↓
向量检索与证据构建层
  ├─ 相似区域检索
  ├─ 可达候选检索
  ├─ 拓扑比较检索
  └─ 变化模式检索
          ↓
LLM 推理层
  ├─ 基于证据的回答生成
  ├─ 空间解释
  ├─ 排名理由说明
  └─ 比较型推理
```

## 5. GeoVeX 借鉴策略

GeoVeX 应被视为架构思想来源，而不是可原样照搬的实现模板。

### 5.1 直接保留

| GeoVeX 思想 | 决策 | 原因 |
|---|---|---|
| H3 风格网格离散化 | 保留 | 它把问题从海量对象训练转化为上下文单元训练 |
| 邻域上下文编码 | 保留 | 它正面解决了局部检索结构弱、区域语义弱的问题 |
| 多圈邻域建模 | 保留 | 它同时支撑局部与区域两种尺度的空间理解 |
| 两阶段训练逻辑 | 保留 | 它能提升稳定性，并把编码器学习和下游使用解耦 |

### 5.2 改造后保留

| GeoVeX 思想 | 决策 | 改造方式 |
|---|---|---|
| 六边形邻域编码器 | 改造后保留 | 先做轻量邻域编码器，完整 masked hex convolution 可以后置 |
| 距离加权空间损失 | 改造后保留 | 使用距离衰减的一致性或对比损失，避免粗暴拉近大区域对象 |
| 稀疏计数重建损失 | 改造后保留 | 可作为辅助目标，但不应成为第一阶段的阻塞项 |

### 5.3 不直接照搬

| GeoVeX 假设 | 决策 | 原因 |
|---|---|---|
| 只建模点对象 | 不照搬 | 目标系统必须支持线和面 agent |
| 用复杂几何中心点代表所有对象 | 不照搬 | 会丢掉拓扑、形状范围和覆盖信息 |
| 默认方向理解可由 cell 语义自然学到 | 不照搬 | 方向仍需要显式监督与辅助任务 |

## 6. 各版本职责

### 6.1 V2.4 的职责

`V2.4` 的职责，是把空间检索做稳定、做可用。

它不负责一次性解决完整城市语义问题。

#### V2.4 必须交付

- 稳定的训练行为
- 可靠的局部邻域保持
- 基于上下文的空间检索能力
- 基于局部上下文的点对象检索
- 为后续方向语义和区域语义打基础

#### V2.4 不应试图一次完成

- 完整功能区分类
- 高质量线要素推理
- 完整面对象语义比较
- 最终用户可见的解释型 RAG 效果

### 6.2 V2.5 的职责

`V2.5` 的职责，是让系统具备空间理解能力，而不是只做更强一点的检索。

#### V2.5 必须交付

- 显式方向敏感性
- 功能区区分能力
- 区域级相似性检索
- 多尺度上下文融合

#### V2.5 不应试图一次完成

- 所有最终面向用户的推理效果
- 完整的时空演化分析
- 在没有 RAG 证据层的情况下直接达成高质量解释能力

### 6.3 V3 的职责

`V3` 是第一个必须按最终用户任务质量来验收的版本。

#### V3 必须交付

- 点、线、面对象的统一检索能力
- 区域相似性推理
- 拓扑感知的比较能力
- 基于证据的回答生成
- 对 LLM 可用的多几何空间智能

## 7. 点 / 线 / 面 agent 职责拆分

这个拆分是强制性的。不同几何类型不能被压扁成同一种泛化对象。

### 7.1 点 agent

点 agent 表示细粒度地点与本地服务设施。

#### 点 agent 必须编码的内容

- POI 的精确身份与类别
- 周边商业与服务语境
- 步行尺度下的邻域相关性
- 类别密度和附近业态混合情况

#### 点 agent 主要承担的任务

- 附近推荐
- 局部相似性检索
- 地点锚点解释
- 高分辨率城市微场景检索

### 7.2 线 agent

线 agent 表示出行结构和拓扑连接关系。

#### 线 agent 必须编码的内容

- 穿越多个 cell 的覆盖序列
- 长度与空间跨度
- 方向分布
- 网络角色
- 对通达性的贡献

#### 线 agent 主要承担的任务

- 路径感知比较
- 公交 / 自驾 / 骑行便利度分析
- 屏障效应和走廊效应分析
- “为什么这个地方可达 / 不可达”的解释

### 7.3 面 agent

面 agent 表示区域语义和空间范围。

#### 面 agent 必须编码的内容

- 覆盖哪些 cell
- 每个 cell 的覆盖比例
- 功能类别或土地利用语义
- 形状范围和边界效应
- 区域内部构成

#### 面 agent 主要承担的任务

- 商圈比较
- 商业 / 住宅 / 混合功能区识别
- AOI / block 级语义检索
- 区域模式解释

### 7.4 几何到网格的投影规则

| 几何类型 | 投影规则 | 说明 |
|---|---|---|
| 点 | 映射到一个主导 H3 cell | 保留精确坐标作为辅助元数据 |
| 线 | 映射为覆盖 cell 序列或采样后的覆盖路径 | 不能退化成一个中心点 |
| 面 | 使用 polyfill 或按覆盖比例映射到多个 cell | 保留面积权重贡献 |

## 8. 功能需求

以下需求在可行处尽量采用 EARS 风格表达。

### 8.1 核心功能需求

- 当用户提出带交通约束的附近推荐请求时，系统应基于空间 embedding 与可达距离约束进行候选检索，而不是只依赖文本相似度。
- 当用户提出区域相似性问题时，系统应基于多尺度空间语义比较区域或面对象，而不是只比较 POI 重合数量。
- 当用户要求比较两个商圈对于某类居民的便利度时，系统应同时使用线要素和拓扑结构特征，而不只是用欧式距离。
- 当用户询问某个商业集群为什么形成时，系统应返回基于教育资源、交通、POI 密度、土地利用与集聚结构的证据。
- 当用户询问功能区时，系统应能够在区域尺度至少区分商业区、住宅区和混合功能区。
- 当用户提出方向敏感问题时，系统应使用显式方向表征，而不是默认方向可由距离关系间接学到。
- 当系统为 LLM 构建向量知识时，系统应支持点、线、面三类 agent 在统一检索框架下工作。
- 当存在时序数据时，系统应支持区域级变化模式检索与解释。

## 9. 非功能需求

### 9.1 规模要求

系统必须面向当前已观测到的武汉级数据规模进行设计：

- 约 `845,676` 个点 agent
- 约 `54,950` 个道路线 agent
- 约 `193,615` 个面 agent，来源于 AOI、landuse、block 等图层
- 总计约 `1.09 million` 个空间 agent

### 9.2 本机硬件约束

目标本地环境约为：

- CPU：`i7-13700HX`
- RAM：`32 GB`
- GPU：`RTX 5060 Laptop GPU，8 GB VRAM`

在此约束下：

- 系统必须避免把百万级 agent 直接作为默认端到端训练对象
- 系统必须以 cell 级压缩作为预训练主路径
- 编码和检索内存开销应尽量由 cell 数量决定，而不是由原始对象数量决定

### 9.3 性能方向

- 离线预处理必须支持批处理和断点恢复。
- 编码器训练必须能够在本机环境下完成，不以分布式集群为前提。
- 检索层必须支持区域级和 agent 级检索，并具备可用于生产的响应延迟。
- 推理层必须始终附带空间证据，而不是只输出生成式解释文本。

### 9.4 鲁棒性

- 几何元数据缺失时，不得静默污染 embedding。
- 稀疏 cell 不得成为训练不稳定的主要来源。
- 大面对象不得抹平局部差异。
- 长道路不得退化成无意义的中心点语义。

## 10. 验收标准

### 10.1 面向用户的验收

#### 场景 A：步行推荐

- 给定一个起点 POI 和步行时长约束
- 当用户请求附近推荐
- 那么系统应返回真实可达的候选对象，并附带距离或时间、排序依据和简短解释

#### 场景 B：相似区域检索

- 给定一个命名商圈或混合功能区
- 当用户请求查找相似区域
- 那么系统应返回 top-k 可比较区域，并附带 POI 结构、土地利用和邻域构成等证据

#### 场景 C：便利度比较

- 给定一个居民来源区域和两个目标商圈
- 当用户询问哪个更方便
- 那么系统应至少从公共交通、自驾或骑行等维度进行拓扑感知比较

#### 场景 D：集群成因解释

- 给定一个高密度商业现象
- 当用户询问其形成原因
- 那么系统应基于周边高校、密度、通达性、土地利用和集聚效应给出有依据的解释

### 10.2 模型层验收

- `V2.4` 应交付稳定的空间检索质量，而不只是较高的距离相关性。
- `V2.5` 应体现出方向区分能力和区域类型可分性。
- `V3` 应能基于多几何类型证据回答区域比较与拓扑感知问题。

## 11. 错误处理表

| 条件 | 期望处理方式 |
|---|---|
| 点 agent 缺少类别或元数据稀疏 | 回退到几何与邻域派生特征，并标注不确定性 |
| 道路线几何无效或被严重切碎 | 暂不纳入线投影，不允许用伪中心点替代 |
| 面对象 polyfill 过粗或覆盖过大 | 保留面积权重，并允许多尺度覆盖 |
| cell 极度稀疏或为空 | 使用重建 / 平滑策略，避免强行学习噪声语义 |
| 方向标签不明确 | 降低置信度或跳过该样本的方向辅助监督 |
| 多种几何证据之间相互冲突 | 展示证据分裂，不强行输出单一不透明结论 |

## 12. 实施清单

### 12.1 V2.4 清单

- [ ] 构建基于 H3 的点、线、面预处理投影管线
- [ ] 在默认尺度和一个更大尺度上构建 cell 级邻域特征
- [ ] 用 cell-context 编码器预训练替换当前以 POI 为中心的训练路径
- [ ] 保留当前距离信号，但不再把它作为唯一优化目标
- [ ] 在武汉级样本上验证稳定的局部检索质量

### 12.2 V2.5 清单

- [ ] 加入显式方向编码与辅助监督
- [ ] 引入区域级功能区语义目标
- [ ] 引入面对象感知的区域表示
- [ ] 评估区域相似性检索，而不是只看点邻居重叠率

### 12.3 V3 清单

- [ ] 把点、线、面 agent 投影到统一检索空间
- [ ] 构建用于 RAG 回答的证据装配层
- [ ] 把区域比较查询做成一等检索任务
- [ ] 支持拓扑感知的便利度与通达性推理
- [ ] 定义面向最终回答质量的用户验收体系

## 13. 最终决策总结

本项目必须由最终用户看到的空间问答质量来牵引，而不是被中间模型指标牵着走。

正确路径不是：

- “只把 POI embedding 做得更好”
- “在当前 MLP 上继续堆更多 loss”
- “把所有几何对象都当成同一种对象处理”

正确路径应是：

- 基于 cell 的空间上下文学习
- 面向点、线、面的差异化投影
- 多尺度空间语义建模
- 拓扑感知检索
- 基于证据的 LLM 空间推理

一句话总结，`V3-GeoEncoder-RAG` 应被设计成一个空间智能系统，而不是一个稍微更强一点的附近搜索模型。
